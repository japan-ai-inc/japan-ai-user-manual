# JAI Adminでリリースを登録・検証導入する

JAI Adminで、内部のStudio ProjectからAppの候補リリースを作成し、許可された内部組織へ検証用に導入する手順です。対象は配布担当者です。

ここでいう「リリース公開」は、選択したソースProjectのスナップショットから不変の候補版を作る操作です。この段階では顧客組織は変更されません。続く検証は、候補版を内部の検証組織へ導入またはデプロイし、導入先のProjectで必要な業務操作を確認する工程です。**候補版を作成したこと、検証インストールが成功したこと、顧客へ配布して利用できることは別です。**

## 始める前に

- JAI Adminの「Studioアプリ配布」を表示・操作できる管理権限があることを確認します。画面を開けない、対象の組織・Project・Appが検索できない、操作が失敗する場合は、権限を推測して変更せず管理担当者へ依頼してください。
- 配布するApp、既存の「アプリID」の有無、ソース組織・ソースProject、対象バージョン、変更内容、検証担当を決めます。既存Appの新しい版なら、そのAppの「既存アプリID」を選びます。
- 配布対象に含めるPage、Agent、Workflow、Skill、Dataset、Object、Storage、設定が依存する接続・Secretを確認します。導入先へ持ち込めない値、固定ID、検証用でない実データは除きます。設計上の確認は[リリースの互換性を管理する](manage-release-compatibility.md)と[配布可能なPageの設定設計](../development/design-distributable-page-config.md)を参照してください。
- 検証に使う内部組織、テスト用のデータ、確認する代表操作、結果を判断する担当者を決めます。顧客組織を検証先に選ぶことはできません。

> 「設定」の「検証組織」は、候補版・ベータ版を検証できる有効な内部組織の許可リストです。このリストを更新できるのはスーパー管理者だけです。配布担当者は、登録済みの検証組織が選べない場合に自分で追加せず、スーパー管理者へ依頼してください。

## 1. 候補リリースを作成する

1. JAI Adminで「Studioアプリ配布」を開き、「リリース公開」を選びます。
2. 「アプリIDを選択または作成」で、既存Appなら「既存アプリID」を選びます。初回なら「新規ID」を選び、表示名と「新規アプリSlug」を確認して「IDを作成して選択」を実行します。アプリIDは、同じAppのリリースとインストールをまとめる名前です。
3. 「ソースStudioプロジェクトから」で「ソース組織」、続けて「ソースプロジェクト」を選びます。既存リリースのあるAppではソースがロックされ、選び直せない場合があります。表示された組織・Projectが想定どおりか確認します。
4. 「ソース公開時の実行ユーザー」が表示される場合は、ソースProjectと対象リソースを読み取り・更新できる有効なメンバーを選びます。これはソースの読み取り・エクスポートに使われ、インストール後の実行ユーザーを決めるものではありません。
5. 「リリースリソーススコープ」で、配布するリソースを確認します。「選択」を使う場合は、必要な対象がすべて含まれること、不要な対象が含まれないことを確認します。依存関係が自動で追加される前提にはしません。
6. Pageのホーム、ナビゲーション、Objectのスキーマ、初期データやStorageのシードを設定する項目が表示される場合は、対象と影響を確認します。初期データを含める場合は、検証環境で既存データへ与える影響も確認します。
7. 「このリリースのバージョン」で未使用の `x.y.z` 形式の「リリースバージョン」を選び、「リリースノート」に変更内容、検証範囲、既知の注意点を記載します。同じAppで既存版を上書きすることはできません。
8. まず「準備状況を確認」を実行します。これはドライランであり、リリース行も顧客組織へのインストールも作成しません。エラーや不足するリソースがあれば、対象・依存・設定を見直してから再確認します。
9. 結果と入力を再確認し、「リリースを公開」を選びます。「リリースを公開しました」と表示されたら、App名、バージョン、含めた対象、リリースノートを記録します。

> リリース公開後にソースProjectを変更しても、作成済み候補版の内容は変わりません。修正が必要なら既存候補を編集するのではなく、変更を確認して新しいバージョンを作成します。

## 2. 検証組織へ導入またはデプロイする

1. 「検証と昇格」を開き、「このリリースを検証」の「リリース」で「候補版またはベータ版リリース」を選びます。
2. 「検証組織へ」で許可済みの「検証組織」を選びます。ここで選べるのは有効な内部組織だけです。顧客への初回導入や顧客組織の変更には、この操作を使いません。
3. 「検証環境」の状態を確認します。

| 状態 | 対応 |
|---|---|
| 「未インストール」 | 初回の検証導入です。「ランタイム所有者」を選び、「検証環境へインストール」を実行します。 |
| 「更新可能」 | 既存の検証インストールがあります。対象Appと現在の検証リリースを確認し、「検証環境へデプロイ」を実行します。 |
| 「最新」 | 選択した候補版がすでに有効です。再実行せず、検証結果を確認します。 |
| 「デプロイ中」 | 完了または失敗の表示を待ちます。重ねて実行しません。 |
| 「前回のデプロイ失敗」 | 結果またはログ、対象リリース、検証先の状態を確認し、原因を修正してから再実行します。初回の有料App導入が失敗した場合は、再試行前にシート購入の確認が必要になることがあります。 |

4. 初回の「検証環境へインストール」では「ランタイム所有者」を選びます。既存の検証インストールへのデプロイでは、そのインストールの実行者が再利用されます。
5. 検証インストールまたは検証デプロイの完了表示後、「検証環境」で「現在の検証リリース」が選択中のリリースと一致すること、「最終デプロイ」に失敗がないことを確認します。

検証導入では、導入先にApp用の環境が作られます。表示上の成功だけで、Page表示、Agent・Workflow実行、データ操作、接続、利用者権限、外部連携まで正常と判断しません。

## 3. 導入先Projectで結果を確認する

検証組織へ切り替え、作成または更新された検証用AppとProjectを開きます。事前に決めたテストデータだけを使い、次を確認します。

- 想定したApp、バージョン、Page・Agent・Workflowなどの入口を開けること
- 代表的な読み取り・入力・実行が、想定した利用者権限で完了すること
- Object、Storage、初期データが必要な場合に、想定した内容・保存先で利用できること
- 接続・Secret・利用者本人の認証が必要な機能は、設定済みか、設定担当者と手順が明確であること
- 自動実行、通知、外部更新を含む場合は、検証で実施してよい範囲と結果を個別に確認したこと

確認結果には、App名、候補バージョン、検証組織・Project、実施日時、実行者、操作、期待結果、実際の結果、未確認項目を残します。APIキー、Secret値、パスワード、アクセストークン、個人情報を記録へ含めません。

> 検証成功は、審査・承認・安定版への昇格を自動で行いません。また、昇格後の配布完了を示すものでもありません。次の判断は[JAI Adminで審査・承認・Stable昇格する](admin-review-approve-promote-stable.md)、掲載情報・価格の確認は[JAI Adminで掲載・価格を管理する](admin-manage-listing-and-pricing.md)で行います。

## うまくいかない場合

| 状況 | 確認・対応 |
|---|---|
| 「Studioアプリ配布」または操作ボタンが表示されない | JAI Adminの管理権限、対象の管理スコープ、利用可能な組織・Projectを管理担当者へ確認します。 |
| 検証組織を検索できない・選べない | 有効な内部組織として許可リストに登録済みかを確認します。リスト変更はスーパー管理者へ依頼します。 |
| 準備状況確認またはリリース公開に失敗する | ソース組織・Project、実行ユーザー、リソーススコープ、依存関係、入力内容を確認します。ソースが変更された旨の表示なら、変更を確認して準備状況確認からやり直します。 |
| 初回導入で「ランタイム所有者」を選べない | 検証組織を先に選び、対象メンバーが有効であることを確認します。既存検証インストールの更新では新たな選択は不要です。 |
| 検証デプロイが失敗する | 「最終デプロイ」の結果・エラー、対象App、選択リリース、検証インストール、導入先の設定を確認します。失敗を顧客展開や安定版昇格で回避しません。 |
| 検証では動くが顧客への影響を判断できない | 互換性、必要な再設定、対象顧客、案内内容を[リリースの互換性を管理する](manage-release-compatibility.md)で整理し、承認・昇格を保留します。 |

## チェックリスト

- [ ] App、アプリID、ソース組織・Project、対象バージョンを確認した
- [ ] 配布対象と依存関係、接続・Secret・固定値を確認した
- [ ] 「準備状況を確認」で不足やエラーを解消した
- [ ] リリースノートに変更内容と検証範囲を記録した
- [ ] 許可済みの内部検証組織を選び、顧客組織を使っていない
- [ ] 検証環境で選択中のリリースと現在の検証リリース、最終デプロイを確認した
- [ ] 導入先Projectで代表操作と必要な設定を確認し、未確認事項を残した
- [ ] 審査・承認・昇格、顧客配布をまだ完了扱いにしていない
