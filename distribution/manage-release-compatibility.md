# リリースの互換性を管理する

Appを更新すると、導入先の画面、業務手順、接続、保存済みデータに影響する場合があります。配布担当者は、候補リリースと現在配布中のリリースを比較し、**既存の導入先を更新しても利用者の準備なしに使えるか**、または**変更・再設定・事前連絡が必要か**を判断します。

この判断は、公開の可否だけを決めるものではありません。安定版への昇格後、準備ができた既存インストールには自動更新が予定されます。更新対象、利用者への影響、確認結果、個別対応が必要な導入先を整理してから進めてください。

## この記事の範囲

対象は、JAI AdminでAppのリリース、検証、安定版への昇格、顧客への配布を担当する方です。作成者による変更の作成・申請、導入先の管理者が行う再設定・業務確認の詳しい手順は対象外です。導入先への案内と確認は[App更新の変更点と再設定を確認する](../use/check-app-updates.md)を参照してください。

互換性は「新しい版が作成できた」ことではなく、**既存導入先の現在の構成・データ・利用手順で、更新後も必要な業務が成立するか**で判断します。JAI Adminに「互換」と表示されることを前提にせず、変更内容と検証結果を記録します。

## 始める前に

- 比較するApp、現在の安定版、候補の「バージョン」、対象顧客組織を確認します。
- 現在の導入先で使われるPage、Agent、Workflow、Object、Storage、接続、Secret、定期実行・外部連携を把握します。
- 変更の作成者、検証担当、顧客窓口、導入先で再設定や業務確認を行う担当者を決めます。
- 顧客へ影響する操作は、検証環境と許可されたテストデータで先に確認します。実データの更新、外部送信、削除を確認目的だけで実行しません。

> 「公開成功」と「全導入先で更新完了」は別です。公開後の自動更新は準備済みの既存インストールを対象に予定されますが、個別の失敗や更新待ちがあり得ます。配布の進捗を確認するまで、全顧客が新しい版を利用できるとは案内しないでください。

## 1. 変更を互換・影響ありに分ける

まず、候補と現在の安定版の構成、変更履歴、導入先の利用実態を突き合わせます。変更がないと確認できない対象は「影響なし」にせず、「未確認」とします。

| 変更対象 | 互換と判断する目安 | 影響ありとして扱う例 |
|---|---|---|
| Page、Agent、Workflow、Skill | 既存の入口、入力、出力、参照先、実行権限で代表操作が完了する | 削除、名前変更、呼び出し先・入力形式・出力形式の変更、利用者の操作変更 |
| Object | 既存レコードと既存の参照・更新処理が新しいスキーマでも成立する | Object・フィールドの削除／名前変更、型・必須性・一意性・既定値・関連の変更 |
| データ・ファイル | 既存の保存先と形式で読み取り・処理ができる | 保存先、ファイル形式、データの意味、初期データの扱いを変える |
| 接続・Secret・権限 | 既存の設定で必要な機能が実行できる | 新しいコネクタ、共有／個人接続、Secret、許可・利用者本人の認証が必要になる。コネクタの追加・変更・削除は、導入後の設定担当と影響利用者を確認する。 |
| 自動実行・外部連携 | 更新後も意図した対象・頻度・通知先で処理できる | 実行条件、通知先、外部サービスへの書込み内容が変わる |

リソースの削除または名前変更は、旧名称への参照を残したままでは互換と判断しません。配布結果でも、削除またはリネームされた管理コンポーネントは、削除と追加として扱われます。旧リソースを参照するPage、Workflow、外部呼出し、運用手順、利用者向け資料を確認してください。

Objectのスキーマ変更は特に慎重に扱います。導入先固有のレコードを保持したまま更新される場合があるため、スキーマを配布できたことだけで、既存レコードや業務処理が安全であるとは判断できません。変更前後の代表レコードで、読み取り、作成、更新、検索、関連するApp機能を確認します。

## 2. 利用者への影響と必要な作業を整理する

影響あり、または未確認の項目ごとに、誰が何をいつ行うかを決めます。顧客へ依頼する作業は、画面に表示される「セットアップ」だけに限定しません。

| 判定 | 配布前に決めること | 利用者への案内 |
|---|---|---|
| 互換 | 検証した導入先・操作、更新後の確認担当 | 変更内容、反映状況の確認方法、問い合わせ先 |
| 再設定が必要 | 接続・Secret・権限・データ準備の担当、完了確認方法 | 実施者、手順、実施期限、完了前に使わない機能 |
| 操作変更がある | 旧手順を止める日、教育・移行の担当 | 新旧の操作差、対象利用者、開始条件 |
| 破壊的変更または未確認 | 自動更新の対象にしてよいか、個別展開・保留・代替策 | 影響範囲、利用停止または回避方法、顧客窓口 |

利用者へは、対象App、対象「バージョン」、変更点、必要な再設定、確認済みの範囲、未確認または利用を見合わせる機能、問い合わせ先を伝えます。導入先の管理者は、更新後に接続・Secret・本人の認証・業務操作を確認する必要がある場合があります。詳細は[App更新の変更点と再設定を確認する](../use/check-app-updates.md)へ案内します。

## 3. リリースの版と進行状況を確認する

リリースには「バージョン」と変更履歴を残します。同じAppで同じバージョンは使えないため、再申請・修正・取り下げ後の作り直しも、配布対象を識別できる新しいバージョンとして管理します。版番号だけで互換性を推測せず、変更履歴と比較結果を必ず併記してください。

JAI Adminの「リリースフロー」では、「候補を公開」→「検証環境へインストール」→「安定版へ昇格」→「顧客展開」または「インストール管理」という流れを確認できます。候補の公開は顧客環境を変更しません。検証に成功したリリースを承認すると安定版として公開され、既存インストールへの自動更新が予定されます。

承認前に、対象版が検証済みであり、変更履歴が利用者向けの説明として不足していないかを確認します。審査画面の「今回の審査対象」「現在公開中の内容」、状態の「審査待ち」「承認済み」「却下済み」「キャンセル済み」も、配布判断の記録に含めます。

> 「安定版へ昇格」は、互換性を自動判定する操作ではありません。破壊的変更、再設定、移行手順があるリリースは、顧客ごとの準備と連絡を確認してから昇格・展開を判断してください。

## 4. 自動更新と手動展開を使い分ける

Marketplaceの詳細では「常に最新版（自動更新）」と表示される場合があります。安定版への昇格では、準備完了している既存インストールが自動更新の対象になります。一方、組織内self-installはこの自動配布の対象外です。

初回インストール、特定顧客だけへの更新、再設定や移行を確認してから進める更新は、「顧客展開」または「インストール管理」で扱います。「詳細デプロイ」は選択したインストールだけを更新するため、影響の大きい変更では対象組織・現行版・担当者を再確認してから実行します。

自動更新の対象でも、組織やインストールが有効であること、現在のリリースがあること、別のデプロイが進行中でないことなどの条件により、直ちに更新されない場合があります。個別の失敗は再試行されるため、顧客に完了を伝える前に「配布の進捗」で対象ごとの結果を確認します。

## 5. リリースノートと完了確認を行う

変更履歴とリリースノートには、少なくとも次を記載します。書き方と掲載場所は[リリースノート](../troubleshooting/release-notes.md)を参照してください。

- App名、バージョン、公開・配布の対象
- 追加・変更・削除した機能とリソース
- 互換性の判定と、影響する業務・利用者
- 必要な再設定、データ移行、操作変更、実施期限
- 自動更新か個別展開か、反映状況の確認先
- 既知の制約、未確認項目、問い合わせ先

## 確認できない場合

変更内容、利用中の旧リソース、Objectの既存レコードへの影響、必要な再設定、対象顧客の更新状況を確認できない場合は、互換と判断して自動更新を前提に案内しません。「インストール管理」で対象を絞る、顧客展開を保留する、作成者・顧客担当者へ確認するなど、影響を限定して対応します。

問い合わせには、App名、現在版と候補版、対象組織、変更対象、実施日時、表示された状態、検証結果、顧客に必要と見込む作業を添えます。Secret値、APIキー、パスワード、個人の認証情報は記載しません。
