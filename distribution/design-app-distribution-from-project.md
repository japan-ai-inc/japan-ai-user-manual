# ProjectからAppへの配布設計

Projectで作った機能をAppとして届けるときは、**同じ組織の利用者へ導入する**のか、**Marketplaceで提供する**のかを最初に決めます。選択によって、公開先、審査、導入者、更新の進み方、問い合わせ先が変わります。

Projectは作成・管理の単位、Appは利用者へ提供する単位です。Projectを作成・共有しただけではAppにならず、Appを作成しただけでもMarketplaceへ掲載されません。用語と関係は[Studio Workspace・Project・App・Marketplaceの関係](../getting-started/studio-concepts.md)を参照してください。

## この記事の範囲

この記事は、作成者が配布経路を選び、公開前から運用終了までの責任分担を設計するためのものです。Appを作成する画面操作、組織内導入、Marketplace公開申請、JAI Adminでの審査・配布操作の詳細は、それぞれの関連記事で確認してください。

画面に「App公開」が表示されない、または操作できない場合があります。表示されない機能を前提に計画したり、権限を自分で広げたりせず、対象の組織・Project・権限・提供条件を管理担当者へ確認します。

## 始める前に

配布経路を決める前に、次を整理します。

- **利用者と導入先**：同じ組織内だけか、Marketplaceを通じた顧客組織も対象かを決めます。
- **Appの境界**：どのPage、Agent、Workflow、Skill、自動実行、Dataset、カスタムオブジェクト、カスタムロール、Project StorageをAppに含め、何を導入先で設定するかを棚卸しします。個別選択やStorageシードには対象ごとの件数・データ量の制限があるため、公開画面と検証結果で確認します。
- **接続と機密情報**：必要なコネクタを、配布物に含める要件と導入先で設定する接続に分けます。Secret値、APIキー、トークン、配布元の接続状態を配布物へ含めません。共有／個人コネクタの別、導入先で設定する担当者、代表確認を決めます。
- **運用責任**：リリースノートの作成者、導入案内の担当者、更新確認者、障害時の連絡先、サポート終了の決定者を決めます。

> 開発元Projectを利用者へ直接共有することと、Appとして導入することは別です。App化しても、配布元固有のID、URL、認証情報、実データが導入先でそのまま利用できるとは限りません。配布可能なPageの設計は[配布可能なPageの設定設計](../development/design-distributable-page-config.md)を参照してください。

## 配布経路を選ぶ

「App公開」では公開先として「組織内」または「マーケットプレイス」を選べます。前者は組織内self-install、後者はJAPAN AIの審査を経るMarketplace配布です。

| 判断項目 | 組織内self-install | Marketplace公開 |
|---|---|---|
| 想定する導入先 | 開発元と同じ組織 | Marketplaceで提供する顧客組織 |
| 公開先の選択 | 「組織内」 | 「マーケットプレイス」 |
| 審査・掲載 | JAPAN AIの審査・Marketplace公開は不要 | 公開申請後、JAPAN AIが審査・提供段階・掲載を管理 |
| 導入の起点 | 作成者側で「この組織にインストール」 | 顧客側がMarketplaceで内容・条件を確認してインストール |
| インストール先 | 開発元とは別の専用Project。利用者とアクセス権を個別に管理 | 顧客組織の導入先。初期設定・利用者設定が必要な場合がある |
| 更新の考え方 | 新しい版を準備し、「インストール済みアプリを更新」で適用結果を確認 | 承認・公開後、既存インストールへの自動更新が予約される。更新完了と利用確認は別に行う |
| 向いている場合 | 社内検証、部門展開、導入先を自分たちで管理する場合 | 複数の顧客組織へ提供し、審査・掲載を経た提供が必要な場合 |

同じAppで両方を使う場合も、経路ごとに対象組織、導入担当、設定値、確認記録を分けます。組織内導入を先に行ったことだけで、Marketplace審査や掲載が済むわけではありません。

## ライフサイクルを設計する

配布は公開時点で終わりません。次の流れを、担当者と確認結果を残せる形にします。括弧内は確認できた画面上の表示です。

```text
リリース準備
  → 審査または組織内導入
  → 正式提供
  → 顧客・利用者のインストール
  → 更新
  → サポート終了・廃止
```

| 段階 | 作成者が決めること | 主な担当・確認 |
|---|---|---|
| リリース準備 | App名、対象リソース、ホーム画面、版、変更内容、導入先で必要な設定を確定します。「公開前チェック」で問題・警告を確認します。 | 作成者。変更内容は「リリースノート」に記録します。 |
| 組織内導入 | 「アプリのリソースを確認」後、準備済み版を対象組織へ導入します。 | 作成者または組織の導入担当。インストール済み版と利用者の動作を確認します。 |
| Marketplace審査 | 「審査に提出」後は、審査が完了するまで同じAppから新しいリリースを提出できません。 | 公開申請者とJAI Adminの配布担当。却下時は理由を確認して修正・再申請します。 |
| 正式提供・掲載 | 承認された版は「正式提供中」となり、Marketplaceの掲載はJAPAN AI側で管理されます。 | JAI Adminの審査・配布担当。作成者は掲載内容と提供版を照合します。 |
| 顧客インストール | 顧客側はインストール後、共通設定、利用者アクセス、個人の接続を確認します。 | 顧客の導入担当・利用者。作成者は必要な設定と問い合わせ先を案内します。 |
| 更新 | 変更内容、設定変更、アクセスへの影響、導入先の反映結果を分けて確認します。 | 作成者、顧客の運用担当、利用者。自動更新の予約は完了確認の代わりになりません。 |
| サポート終了 | 代替版、利用停止日、保存・引き継ぎ、問い合わせ窓口を決めます。提供中の版を「廃止」にする影響と、既存導入の扱いを個別に確認します。 | 作成者、顧客の責任者、JAI Adminの配布担当。アンインストールは顧客側で実施する場合があります。 |

Marketplaceの詳細な連携は、[Marketplaceへ公開申請する](submit-to-marketplace.md)、[JAI Adminでリリースを登録・検証導入する](admin-register-and-test-install-release.md)、[JAI Adminで審査・承認・Stable昇格する](admin-review-approve-promote-stable.md)、[JAI Adminで顧客へ配布・更新確認する](admin-distribute-and-check-updates.md)、[JAI Adminで掲載・価格を管理する](admin-manage-listing-and-pricing.md)で扱います。

> 「承認・公開」や「正式提供中」は、顧客の設定完了、すべての更新完了、利用者が業務を完了できることを意味しません。接続、Secret、アクセス、代表業務を導入先・利用者の条件で確認してください。

## 役割を分ける

| 役割 | 主な責任 |
|---|---|
| 作成者 | 配布対象、依存、リリースノート、導入手順、変更・終了の影響を明確にします。 |
| 公開申請者 | Marketplaceに出す内容を確認し、審査中・却下・承認の状態を追跡します。作成者と同一とは限りません。 |
| 組織内の導入担当 | 対象組織へのインストール、共通設定、利用者アクセス、導入後確認を行います。 |
| 顧客の導入・運用担当 | Marketplaceからの導入、組織固有の接続・Secret・メンバー設定、更新後の業務確認を行います。 |
| JAI Adminの審査・配布担当 | Marketplace経路の審査、承認、提供段階、掲載、顧客配布の管理を行います。 |
| 利用者 | 付与されたAppで業務を行い、個人認証が必要な場合は自分の設定を完了し、利用上の問題を連絡します。 |

## よくある誤解

| 誤解 | 正しい考え方 |
|---|---|
| Projectを共有すればApp配布は不要である | 共同で構築・利用するだけならProject共有を選べます。利用者向けに分離したAppとして届ける必要があるかを先に判断します。 |
| 組織内導入をしたのでMarketplaceにも公開された | 組織内導入とMarketplace公開は別の公開先です。後者には公開申請とJAPAN AIの審査・管理が必要です。 |
| 承認されれば顧客はすぐ使える | 導入、共通設定、個人接続、アクセス、代表業務の確認が残る場合があります。 |
| 自動更新なら確認は不要である | 更新の予約・反映と、導入先の設定・業務結果は別です。変更点と利用者条件で確認します。 |
| 廃止すると顧客のAppも直ちに削除される | 今後の提供と既存導入の削除は別に扱います。影響、保存、アンインストールの担当を決めます。 |

## 確認できない場合

公開先、必要な権限、導入先の設定担当、更新・廃止時の影響を確定できない場合は、公開・提出・導入を進めません。対象のApp、開発元Project、想定組織、利用者、含めるリソース、必要な接続、確認済みの画面表示を記録し、組織の管理担当者またはJAPAN AIの配布担当へ確認します。Secret値、APIキー、トークン、実データは問い合わせに含めません。
