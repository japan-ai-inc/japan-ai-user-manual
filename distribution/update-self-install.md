# 組織内self-installを更新する

組織内self-installで導入済みのAppへ、開発元Projectの変更を反映する作成者向けの記事です。更新は、開発元を直接共有したり、Appを新規に導入し直したりする操作ではありません。**同じインストール先Project**へ準備済みの新しい版を適用します。

更新前には、変更したリソース、アクセス設定、認証情報の要件、利用者への影響を確認してください。Appの利用者・管理者が行う変更点確認、接続・Secretの再設定、業務確認は、[App更新の変更点と再設定を確認する](../use/check-app-updates.md)を参照します。

## この記事の範囲

対象は、組織内のAppを作成し、すでに同じ組織へself-installした**作成者**です。App公開画面で更新版を準備し、既存のインストール先Projectへ適用するところまでを扱います。

Marketplaceの公開審査、他組織・顧客への配布、利用者側だけで行う初期設定は対象外です。組織の設定または権限により「App公開」「組織内のアプリ」が表示されない、準備・更新が実行できない場合があります。必要な権限を持つProjectの編集者または管理者が、準備・インストール・更新を実行できます。

> 開発元でリソースを編集しただけでは、導入済みAppは変わりません。更新対象の版を準備し、内容を確認してから「インストール済みアプリを更新」を実行し、導入先で結果を確認してください。

## 始める前に

- 対象の組織、開発元Project、App名、インストール先Projectを確認します。似た名前の別Appや開発元Projectを対象にしないでください。
- 現在の「インストール済みバージョン」、利用者、利用中のPage・Agent・Workflow、外部連携、定期実行を記録します。APIキー、パスワード、Secret値、トークンは記録・共有しません。
- 変更内容を、追加・削除・変更に分けます。特にロール、アクセスポリシー、オブジェクトのレコードアクセスルールを変える場合は、更新後に誰が何を読取り・更新できるかを事前に確認します。
- 利用者へ影響する時間帯、確認担当、外部送信やデータ更新を伴わない検証方法を決めます。

## 1. 開発元の変更を確認する

1. 開発元Projectで、配布するリソースと依存関係を確認します。開発元固有のID、URL、接続、Secret値を固定したままにしないでください。設計の確認は[配布可能なPageの設定設計](../development/design-distributable-page-config.md)を参照します。
2. Project設定の**「App公開」**を開き、**「組織内のアプリ」**で対象Appを選びます。
3. 導入先の「インストール済みバージョン」と、これから反映する変更を照合します。現在の版が最新である場合は、不要な更新を実行しません。
4. 利用者向けに、変更点、確認が必要な業務、再設定の可能性、問い合わせ先を準備します。利用者側の進め方は[App更新の変更点と再設定を確認する](../use/check-app-updates.md)を参照します。

## 2. 新しい版を準備する

1. **「アプリのリソースを確認」**を実行します。この確認は、選択したリソースを組織内へ導入できるかを確認するものであり、Marketplaceの公開審査への提出ではありません。
2. 確認結果で、追加・削除・変更されるリソースを確認します。件数だけでなく、表示される名称と、導入先の業務への影響を確認してください。
3. 認証情報とコネクタの要件を、現在と新しい版で比較します。「プロジェクトで共有」と「ユーザーごとに設定」のどちらが必要か、追加・変更・削除されるコネクタ、設定または引継ぎの対象を確認します。
4. アクセス設定の変更に関する案内がある場合は、対象リソースのロール、アクセスポリシー、レコードアクセスルールを確認します。利用者が使えなくなる、または不要な利用者へアクセスが広がる変更を、そのまま適用しないでください。
5. 「リソースの確認が完了しました。」が表示されたら、準備する版、含まれるコンポーネント数、変更内容を確認します。確認に失敗した場合は、未解決の参照・依存関係・設定を直し、成功するまで更新へ進みません。

> 「リソースの確認」は、導入先での全業務処理、外部サービスとの通信、利用者全員の認証が成功することを保証しません。更新後に、実際の利用条件で確認が必要です。

## 3. 導入済みAppへ適用する

1. 準備済みの版を確認し、**「インストール済みアプリを更新」**を選びます。
2. 確認画面で、**「インストールするバージョン」**、**「現在のインストール済みバージョン」**、確認対象のコンテンツ、含まれるコンポーネント数、認証情報のスロットを照合します。
3. 追加・削除・変更されたリソース、認証情報の要件、アクセス設定の影響を再確認します。
4. 内容に問題がなければ、確認画面の**「インストール済みアプリを更新」**を確定します。
5. 「処理を受け付けました。反映状況を確認してください。」と表示された場合は、続けて同じ操作をしません。処理中は「インストールまたは更新中です。この画面で状態を自動確認します。」と表示されます。
6. 完了後に**「インストール済みバージョン」**が意図した版であることを確認し、**「インストール済みアプリを開く」**からインストール先Projectを開きます。

更新後の利用者確認、接続・Secretの確認、業務操作のテスト、利用者への案内は[App更新の変更点と再設定を確認する](../use/check-app-updates.md)に従います。[Appの組織内導入](../labs/deploy-app-in-organization.md)のStep 5は、Pageの小さな変更を更新として確認する例です。

## 更新で保持されるもの・更新されるもの

確認画面には、既存のユーザー、認証情報、顧客所有のデータは、管理対象リソースの移行ルールに従って保持されると表示されます。一方、更新版に含めた管理対象リソースとアクセス権は、準備画面で確認した差分に従って移行されます。次のように分けて扱ってください。

| 対象 | 更新時の扱い | 作成者の確認 |
|---|---|---|
| インストール先Project | 新しく作り直さず、同じProjectへ適用します。 | 開発元Projectと導入先Projectを混同しません。 |
| ユーザー・認証情報・顧客所有のデータ | 管理対象リソースの移行ルールに従って保持されます。 | 「保持される」ことだけで利用可能と判断せず、必要な共有認証情報、各利用者の個人接続、業務データを確認します。 |
| 管理対象リソース | 新しい版の追加・削除・変更が反映対象です。 | Page、Agent、Workflow、Object、Storageなどの変更を確認し、導入先で管理対象外のデータを上書きする前提にしません。 |
| アクセス権 | 版に含めたロール、アクセスポリシー、レコードアクセスルールの変更が影響します。 | 最小限の実利用者で、更新前後の閲覧・実行・更新可否を確認します。 |
| 初期投入用のデータ・ファイル | App管理の初期投入内容は、版の移行ルールに従い追加・変更・削除され得ます。 | 利用者が入力・作成したデータやファイルと同じ場所・名前を使わない設計にします。衝突が起きる場合は更新を止めます。 |

認証情報の要件が変わる版では、既存の共有認証情報の修復、または各ユーザーによる個人アカウントの接続が必要になる場合があります。認証情報の値を作成者が利用者へ配布したり、画面・ログ・問い合わせに含めたりしないでください。設定担当者と利用者の役割を分け、[App更新の変更点と再設定を確認する](../use/check-app-updates.md)の手順で確認します。

## うまくいかない場合

| 状況 | 確認・対応 |
|---|---|
| 更新ボタンが使えない、または「新しいバージョンを準備してください。」と表示される | 対象App、開発元Project、準備済みの版、権限を確認します。先に「アプリのリソースを確認」を実行し、準備済みの版を確認します。 |
| リソース確認が失敗する | 未解決の参照、配布に含めていない依存リソース、固定された環境固有の設定を確認します。推測して導入先の権限やSecretを変更しません。 |
| 競合・差分の判断ができない | 現在の版と準備済み版のリソース・認証情報・アクセス設定を確認します。特に利用者のデータや初期投入データと同じ対象を変更する場合は、影響を整理してから再準備します。 |
| 結果が不明、通信が切れた | 直ちに再実行せず、**「インストール状況を再確認」**で現在の版と状態を確認します。画面には、完了している可能性があるため、再試行前に現在の版と状態を確認するよう案内されます。 |
| 「前回のデプロイに失敗したか、追加対応が必要です。」と表示される | 現在の版とエラー表示を確認します。必要なら**「認証情報を管理」**で認証情報を修復し、**「デプロイを再試行」**または修正した新しい版の準備を検討します。 |
| 更新後に利用者が使えない | Appの版、アクセス権、共有認証情報、本人の個人接続、Project Secret、実行結果を分けて確認します。[App更新の変更点と再設定を確認する](../use/check-app-updates.md)に従い、利用者の本来の権限で確認します。 |

### ロールバックについて

更新が失敗した場合、適用処理は失敗した段階までの管理対象リソースを元の状態へ戻す処理を行います。ただし、作成者が画面から任意の過去版を選んで戻す操作は、この確認範囲では確認できません。また、ロールバック処理自体が完了したこと、利用者のデータ・外部サービス側の操作・認証状態まで元に戻ることを、表示だけで断定しないでください。

したがって、失敗時は再インストールや連続更新を先に行わず、**「インストール状況を再確認」**で現在の版・状態を確認します。エラー、対象組織、App名、開発元／インストール先Project、操作日時、変更したリソース、認証情報要件の差分を記録して、配布担当者またはサポートへ相談してください。Secret値、APIキー、トークン、パスワード、顧客データは送らないでください。

## 完了チェック

- [ ] 対象の組織、開発元Project、App、インストール先Project、現在の版を確認した
- [ ] 「アプリのリソースを確認」で、追加・削除・変更と依存関係を確認した
- [ ] 認証情報の要件と、ロール・アクセスポリシー・レコードアクセスルールの変更を確認した
- [ ] 「インストール済みアプリを更新」の確認画面で、現在の版と準備済みの版を照合した
- [ ] 更新後にインストール済みバージョンを確認し、インストール先Projectで代表操作を確認した
- [ ] 利用者・設定担当者へ変更点、必要な再設定、確認済みの範囲を伝えた
- [ ] 結果が不明または失敗した場合、再実行前に「インストール状況を再確認」した
