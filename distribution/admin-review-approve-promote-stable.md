# JAI Adminで審査・承認・Stable昇格する

JAI Adminの「アプリ審査」は、公開申請されたリリースを配布担当者が確認し、承認または却下する画面です。承認は単なる掲載可否の記録ではありません。検証済みの対象リリースを「安定版」として公開し、現在の公開版を置き換え、条件を満たす既存インストールへの自動更新を予定します。公開成功、配布開始、各顧客環境での更新完了は別の状態です。

公開申請者が行う申請・修正は[Marketplaceへ公開申請する](submit-to-marketplace.md)を参照してください。ここでは、配布担当者がJAI Adminで行う審査判断と、その影響の確認だけを扱います。

## この記事の範囲

対象は、JAI Adminで配布運用を担当する方です。導入先の顧客管理者がMarketplaceからAppを選定・インストールする操作、作成者が行う申請の作り直し、料金や利用人数の判断は対象外です。料金・シートの扱いは[Appの利用人数・料金・契約上限を確認する](../operations/check-app-seats-pricing-and-limits.md)を正本とします。

「アプリ審査」を閲覧できることと、決定できることは別です。審査一覧を開けても「承認する」「却下する」が操作できない場合は、必要なJAI Adminの権限を持つ担当者へ依頼します。権限を得るために、対象Appや申請の状態を変更しないでください。

> 承認は取り消し前提の試用操作ではありません。承認すると、対象版を現在の安定版へ切り替えるとともに、顧客向けの公開内容と配布処理に影響します。対象App、バージョン、現在公開中の版、検証結果、顧客影響を確認してから確定してください。

## 承認前に確認すること

「アプリ審査」で状態を「審査待ち」に絞り、App名、申請元、対象「バージョン」、提出日時を確認します。検索結果だけで判断せず、対象を開いて次を突き合わせます。

| 確認対象 | 確認する内容 | 判断上の注意 |
|---|---|---|
| リリース | 対象版、変更履歴、含まれる構成、必要な認証情報・権限 | 版番号が新しいだけで互換とは判断しません。変更内容と検証結果を確認します。 |
| 検証 | 許可された検証環境で対象版の導入またはデプロイが完了し、代表操作を確認したこと | 検証環境への配布完了だけで、顧客環境の設定・業務結果まで保証しません。 |
| 掲載内容 | 「今回の審査対象」と「現在公開中の内容」の説明、画像・動画、変更内容 | 候補作成後に公開版が変わっている警告があれば、置換対象を再確認します。 |
| 顧客影響 | 接続・Secret・データ・利用手順の変更、再設定や案内の必要性 | 影響が未確認なら、安定版昇格や自動更新を前提にしません。詳細は[リリースの互換性を管理する](manage-release-compatibility.md)を参照します。 |

承認には、対象リリースが検証済みであること、審査可能な状態であることが必要です。Marketplace掲載内容があるAppでは、変更履歴が空のままでは公開できません。また、掲載内容が固定されていないと表示される対象は、承認せずに新しいバージョンの作成を依頼します。

## 1. 審査対象と現在の公開版を比較する

1. JAI Adminの「アプリ審査」を開きます。
2. 「審査待ち」から対象を選び、App名、提供元、対象「バージョン」、提出者、提出日時を確認します。
3. リリースの内容、必要な認証情報、変更履歴を読み、[JAI Adminでリリースを登録・検証導入する](admin-register-and-test-install-release.md)で記録した検証結果と照合します。
4. 「今回の審査対象」と「現在公開中の内容」を比較します。画面に「現在の公開Release: 現在の版 → 対象版」と表示される場合は、切替先と切替元を記録します。
5. 対象の説明・画像・動画が、利用者へ提示してよい内容かを確認します。候補に固定された掲載内容が、承認時にリリースとともに公開されます。

> 「掲載プレビュー」が正しいことは、導入先での動作や更新完了の証明ではありません。掲載内容、配布物、顧客環境での動作を別々に確認してください。

## 2. 承認してStableとして公開する

1. 検証・互換性・掲載内容・顧客影響の確認結果を記録します。
2. 対象画面で「承認する」を選びます。
3. 確認画面で対象「バージョン」と、現在の公開版から対象版への切替を再確認します。
4. 「承認すると安定版として公開され、対象の既存インストールへの自動更新が予定されます」という影響を確認し、問題がなければ確定します。
5. 結果が「承認済み」になり、対象版が「安定版」として公開されたことを確認します。続けて配布の進捗で、顧客ごとの結果を確認します。

公開時には、対象版が現在の安定版となり、固定された説明・画像・動画も同時に公開されます。Marketplaceアイコンも更新対象になります。既存インストールへの更新は、利用可能な導入先を対象に予定されますが、組織・インストールが有効であること、現行リリースがあること、別の配布が進行中でないことなどの条件があります。個別の失敗があっても、昇格そのものは取り消されません。

そのため、**「承認済み」または「公開中」と「顧客の更新完了」を同じ意味で扱わないでください。** 導入先ごとの有効な版、失敗・待機の有無、必要な再設定を[JAI Adminで顧客へ配布・更新確認する](admin-distribute-and-check-updates.md)および[App更新の変更点と再設定を確認する](../use/check-app-updates.md)で確認してから、利用開始・更新完了を案内します。組織内self-installは、この自動配布の対象外です。

### 手動の「安定版へ昇格」を使う場合

「安定版へ昇格」は、承認済みのベータ版や内部リリースを扱うための操作です。一方、審査対象リリースは「承認する」ことでStableとして公開されるため、通常は別途の昇格操作は不要です。手動昇格を行う場合も、検証済みであること、現在公開中の版を置き換えること、自動デプロイが予定されることを確認します。

## 3. 却下して修正を依頼する

却下は、対象リリースを公開しない決定です。「却下する」を選び、理由を具体的に入力して確定します。却下理由は10文字以上、2,000文字以下です。再現条件、確認できなかった項目、修正が必要な掲載情報またはリリース内容、再確認条件を残してください。

却下後、対象は「却下済み」となり、そのリリースはStableへ昇格しません。申請者には、却下理由を確認して新しいバージョンを作成し、必要な検証をやり直してから再申請するよう依頼します。既存の公開版や既存インストールを、却下だけで新しい版へ更新することはありません。

## 判断と記録のチェックリスト

- [ ] 対象App、提供元、対象バージョン、現在公開中の版を確認した
- [ ] 検証環境での成功と、代表操作の確認結果を記録した
- [ ] 変更履歴、掲載内容、固定された画像・動画を確認した
- [ ] 互換性、再設定、顧客への案内、自動更新の影響を確認した
- [ ] 承認後も顧客ごとの更新完了を別途確認する計画にした
- [ ] 却下時は、申請者が対応できる具体的な理由を残した

## 監査と確認できない場合

審査の決定には、対象リリース、申請者、審査者、提出・決定日時、状態、コメントが記録されます。承認・却下の操作は監査対象です。問い合わせや引き継ぎでは、App名、対象バージョン、リリース識別子、現在公開中の版、検証結果、決定日時、決定理由、配布進捗を渡します。Secret値、APIキー、パスワード、認証トークン、顧客データを審査コメントや問い合わせに含めないでください。

次の場合は承認・昇格を確定せず、対象の検証・掲載情報・配布状態を再確認します。

- 「検証インストールを正常に完了してください」と表示される。
- 対象がベータ版でない、掲載情報の固定がない、または変更履歴が不足している。
- 現在の公開版が候補作成後に変わり、置換の影響を判断できない。
- 変更が接続、Secret、データ、権限、利用手順へ与える影響を確認できない。
- 公開後の配布結果、顧客環境の有効版、失敗理由を確認できない。
