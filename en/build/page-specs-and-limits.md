# Page Specifications and Limits

A Page is a web screen used within a Project. Creators and developers register **the Page's source** as a ZIP. Studio installs dependencies and runs the build for the registered source, then starts it as a Page. After registration, confirm that it can be opened as a Page, meets access conditions, and produces correct business-processing results. Acceptance of the ZIP or a screen displaying once does not necessarily mean that data integration, authentication, and external sending can also be used correctly.

For screen operations to register and publish, see [Register and Publish a Page from the Screen](register-and-publish-pages.md). For procedures to create and apply versions, see [Manage Page Versions](manage-page-versions.md).

## Key points

| Item | Rule |
|---|---|
| What you register | The Page **source**, not finished build output. Place `package.json` and a lockfile at the root, or `index.html` for a static Page. |
| What Studio does | Selects Bun, Node.js, or static serving based on the lockfile, installs dependencies, runs the `build` script, and starts the Page as a Node.js or Bun server. |
| Rejected ZIPs | Uploaded Next.js build output, and ZIPs with neither `package.json` nor `index.html` at the root. |
| Time to display | After registration or update, the first display can take several minutes (up to about 15 minutes). A build-in-progress screen appears meanwhile, and a build-failure screen appears if the build fails. |
| Server processing | Listen on `process.env.PORT`. The first SSR response has a limit of about 60 seconds. |
| Secret values | Do not put them in files sent to the browser. Reference them as server-side environment variables with `${secret:secret_name}` in the root `.env` or `.env.production`. |

## Scope of this article

This article summarizes conditions checked at registration, build and runtime conditions, access modes, versions, and limits for Pages registered as ZIPs from Studio. It does not cover an individual Page's screen design, data operations, external-service connection settings, or how to create server processing. For source structure and framework settings (such as basePath), see [Page Source Structure and Runtime](../development/page-source-structure-and-runtime.md); for server processing and environment variables, see [Page Server Processing, Environment Variables, and Secret References](../development/page-server-env-and-secrets.md).

## Specifications

| Item | Specification | Notes |
|---|---|---|
| Registration format | With "Upload ZIP," select one ZIP file. Files other than ZIP files and multiple selections are not accepted. | The filename extension and ZIP format are checked. |
| ZIP contents | Put the full Page source in the ZIP. The root must contain `package.json` and a lockfile (Node.js or Bun project), or `index.html` (static Page). A ZIP with neither cannot be registered. | Uploading build output generated by Next.js (for example, by `next build`) is rejected. The build runs on the Studio side, so register the source. |
| Files in the ZIP | Ordinary files in the ZIP are handled as Page files. A ZIP whose paths include elements representing the current or parent directory causes a structure error. | If a ZIP has only one parent folder with all files under it, it is handled without that parent folder. Do not add unnecessary parent folders. |
| Content excluded from registration | Paths containing `__MACOSX`, `node_modules`, `.git`, `.DS_Store`, `.jai-studio`, `__staging`, `__upload-lock.json`, `__backup`, or `__versions` are excluded. In addition, `.next`, `dist`, `build`, `out`, `.cache`, `coverage`, `.turbo`, `.vercel`, `tmp`, and `temp` at the top level of the ZIP (or immediately below a single parent folder in a ZIP wrapped by one) are excluded. | Dependencies and build output are created on the Studio side, so you do not need to include `node_modules` or build output folders in the ZIP. |
| Empty or invalid ZIP | If the ZIP is completely empty, "The ZIP file did not contain any files." appears. If all files are in excluded folders, a message that the ZIP structure is invalid appears. | Check that the source is at the top level of the ZIP, and recreate it. |
| Page name | When registering a new Page, its name is based on the ZIP filename without the extension. | If one Page with the same name is found and you have update permission, it is registered as "Upload new version" after confirmation. Changing the display name does not change registered file content. |
| Runtime and build | Bun, Node.js, or static serving is selected based on the lockfile. For Node.js and Bun projects, dependencies are installed, the `build` script in `package.json` runs, and the Page starts as a Node.js or Bun server. | A build runs at each registration and each application of a new version. A dedicated build-in-progress screen appears, and the first display can take several minutes (up to about 15 minutes). If the build fails, a build-failure screen appears. |
| Conditions for server processing | The server listens on the port specified by `process.env.PORT`. Reserved keys such as `PORT`, `NODE_ENV`, and `PRS_*` are not passed as Page environment variables. Paths such as `/api/v1/*` and `/api/storage` are used by the platform. | The first SSR response has a limit of about 60 seconds. |
| Static Page | A Page with `index.html` at the root is served statically. | Requests to paths that do not exist fall back to `index.html`, and `<base href>` is inserted automatically. |
| Browser-run portion | Screen files (HTML, JavaScript, CSS, initial display data, and so on) are handled on the assumption that they reach users' browsers. | Do not include passwords, API keys, tokens, or Project Secret values. This applies regardless of visibility. |
| Environment variables and `.env` | For a directly uploaded Page, only the root `.env` and `.env.production` are read. Other `.env.*` files are ignored. | Server-side processing reads environment variables from `process.env`. |
| Project Secret | When you write `${secret:secret_name}` in `.env`, the Project Secret with the same name in the same Project is resolved directly and passed as a server-side environment variable. For direct uploads, there is no screen for associating Secrets. | Project Secrets can be read only by Page server environment variables and API call nodes; Agents cannot read them. Prefix-based rejection and the step for selecting secrets exist only in the App publishing and installation flow. **Do not return a Secret value to the browser, display it on the screen, or put it in browser-side variables, logs, or distributed files.** For details, see [Page Server Processing, Environment Variables, and Secret References](../development/page-server-env-and-secrets.md) and [Register, Update, and Delete Project Secrets](../operations/manage-project-secrets.md). |
| Access modes | In "Access Settings," you can select "Sign-in required," "Sign-in optional," or "Anonymous only." "External customer auth" may also appear depending on organization settings and Page status. | "Sign-in required" requires sign-in and Page access permission. "Sign-in optional" and "Anonymous only" allow anyone to open the Page, so check displayed data and operations that can run individually. You can select external customer auth only when using a configured customer ID provider. Configure at least one connection and up to the maximum shown on the screen. |
| Shared URL | A public URL appears for "Sign-in optional" and "Anonymous only." An access URL appears for external customer auth. | A public URL has the form `/p/{token}`. Links built by hand as `/app/...` do not work correctly, so use the URL shown on the screen. Before providing it, check users, displayed information, and execution permissions on the assumption that anyone who knows the URL can reach it. |
| Versions | The first version is created when registering a new Page. Registering a new ZIP to an existing Page switches the current Page content to the new version. You can apply a past version again with "Restore and apply." | The current Page always refers to one "Applied" version. Editing its name or description does not switch content. For detailed procedures, see [Manage Page Versions](manage-page-versions.md). |

## Limits and limit values

| Target | Limit or limit value | Conditions |
|---|---:|---|
| ZIP file size | 100 MB or less | Applies to the compressed ZIP for both "Upload ZIP" and "Upload New Version." A ZIP over 100 MB cannot be registered. |
| ZIP entry count | 5,000 or less | Total files and folders. Checked both against the ZIP central-directory count and during extraction. |
| Total extracted size | 200 MB or less | Total files expanded for registration. Checked separately from compressed ZIP size. |
| ZIPs selectable at the same time | 1 | Number of files selectable on the upload screen. You cannot register multiple ZIPs together. |
| Time to first display | Up to about 15 minutes | Includes installation and build after registration or update. The build-in-progress screen appears during this time. |
| First SSR response | About 60 seconds | Limit from server start until the first response is returned. |
| Pages in the organization | Organization-level limit | You can check the current count and limit in the usage bar on the Page list screen. |
| Project Secret name | 64 characters or less | It must start with a lowercase English letter; subsequent characters can be lowercase English letters, numbers, or underscores. Empty strings and UUID-formatted names are not accepted. |
| Project Secret value | 8,192 characters or less | Empty values cannot be registered or updated. Values are masked in the screen list and details. |
| Page environment variable value | 4,096 bytes or less per value | Even if a value can be saved as a Project Secret, the Page fails at startup if it exceeds 4,096 bytes. Multibyte characters such as Japanese take several bytes per character. |

## Common misconceptions

### Register a ZIP of build output created locally

It is the other way around. Studio installs and builds the registered source. Put the source, with `package.json` and a lockfile (or `index.html` for a static Page) at the root, in the ZIP. Uploading Next.js build output is rejected.

### Sign-in optional and anonymous access are the same

Both are options that let anyone open a Page, but their screen descriptions differ. With sign-in optional, signed-in users use the Page as they are; anonymous access does not require sign-in. Before sharing a public URL in either case, check information displayed and operations that can run in the Page.

### A Secret may be kept on the client side if it has a disguised variable name

Even if you change a variable name, a value sent to a browser can potentially be obtained by users or developer tools. Receive Secret values as server-side environment variables via `${secret:secret_name}` in `.env`, and do not include them in distributed content, browser configuration, screens, or logs. Masking values in the Project Secret management screen and not exposing values on the Page are separate checks.

### You can notify users immediately after uploading a new version

After upload, installation and build run, and display can take up to about 15 minutes. Even if the build succeeds, successful authentication, data retrieval, updates, and external sending are not guaranteed. After checking the applied version, verify representative operations and results from the expected permission and user entry point.

## If something does not work

Do not guess and recreate the ZIP or loosen publishing settings in the following situations.

- An error appears regarding ZIP structure, capacity, entry count, or extracted size.
- A build-failure screen appears, or the build-in-progress screen remains after about 15 minutes.
- After registration, a blank screen, loading error, or required-file loading failure occurs.
- Access-mode options, public URLs, or external customer auth do not appear.
- You do not know how to configure processing that needs a Secret safely.
- You do not know the applied version, Page name, target Project, or execution result.

Record the target organization, Project, Page name, ZIP filename, occurrence date and time, displayed message, reproduction steps, and confirmed operations. Do not attach Secret values, passwords, API keys, tokens, or credentials to an inquiry. For build and display issues, see [A Page Fails to Build, Start, or Display](../troubleshooting/page-build-start-display-failures.md); for Secret configuration, see [Register, Update, and Delete Project Secrets](../operations/manage-project-secrets.md).
