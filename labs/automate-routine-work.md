# 定型業務の自動化

この実習では、架空の日報を要約・分類するWorkflowを作り、下書きと公開後の実行結果を比べます。外部送信、データ更新、トリガー、スケジュールは追加しません。入力にない日付・担当者・決定を補わないことを確認し、最後に実習用Workflowを整理します。

## 始める前に

- Workflowを作成、編集、実行、公開できる検証用Projectを開きます。表示されない場合は、権限や提供条件を[制限・提供条件の索引](../operations/limits-and-availability-index.md)で確認します。
- 既存の業務用Workflowを編集せず、架空の入力だけを使います。下書きのテストも実行であるため、外部送信や更新を行うノードは追加しません。
- ノードの構成、変数、テスト、公開の詳しい操作は、各Stepのリンク先を正本とします。

## この実習で使うサンプル

| 項目 | 値 |
|---|---|
| Workflow名 | 日報整理（実習用） |
| 説明 | 日報テキストを要約・分類する。外部送信・更新は行わない。 |
| 入力変数 | `daily_report` |
| 出力変数 | `summary_result` |

テスト時には次を入力します。

```text
本日の対応：製品説明会の資料を更新し、社内レビューを実施した。
進捗：説明会の構成は合意済み。デモ環境の確認を明日行う。
課題：資料内の価格表記について営業確認が必要。
明日の予定：デモ環境を確認し、価格表記の確認依頼を出す。
```

LLMノードには次の指示を設定し、日報部分には開始ノードの入力変数を画面の候補から挿入します。

> 次の日報だけを根拠に、要約、進捗、課題、予定、要確認の順で日本語に整理してください。入力にない事実、期限、担当者、数値は推測しないでください。要確認事項がなければ「なし」と記載してください。

## Step 1. 下書きの骨格を作る

**目標：** 入力、文章処理、出力を分けたWorkflowを作ります。

1. Workflowの作成画面でサンプルの名前と説明を設定します。
2. 開始ノード、LLMノード、終了ノードを追加し、開始から終了まで接続します。
3. ノードの位置ではなく接続線を確認し、**「チェックリスト」**で不足項目を確認します。
4. **「一時保存」**し、実習用の下書きであることを確認します。

ノードの追加・接続は[Workflowのノードを構成する](../build/configure-workflow-nodes.md)を参照してください。**確認ポイント：** 開始から終了まで到達する接続があり、外部へ送信・更新するノードはありません。

## Step 2. 入力と出力の受け渡しを設定する

**目標：** 日報をLLMへ渡し、整理結果をWorkflowの結果にします。

1. 開始ノードに日報用の入力フィールドを追加し、変数名を`daily_report`、表示名を「日報テキスト」にします。
2. LLMノードにサンプルの指示を入れ、画面の候補から`daily_report`を挿入します。文字として変数名を打つだけでは参照になりません。
3. 終了ノードに`summary_result`を追加し、LLMの文章出力を選びます。
4. **「一時保存」**後に、入力参照と終了出力を開き直して確認します。

変数の作成・参照・出力は[Workflowの変数・分岐を設定する](../build/configure-workflow-variables-and-branches.md)を参照してください。**確認ポイント：** `daily_report`はLLMの入力参照であり、`summary_result`はLLMの出力を参照しています。

## Step 3. 下書きを一度実行する

**目標：** 公開前に、入力・各ノード・最終結果を照合します。

1. 編集画面の実行操作から手動の開始ノードを選びます。
2. サンプルの日報を入力し、**「実行を開始」**を一度だけ選びます。
3. 結果で`summary_result`を確認し、要約、進捗、課題、予定、要確認が区別されているか確認します。
4. ステップの詳細で、開始入力、LLMの入出力、終了出力を順に照合します。

下書きの実行と結果の見方は[Workflowの下書きをテストする](../build/test-workflow-drafts.md)を参照してください。**確認ポイント：** 「価格表記について営業確認が必要」が残り、入力にない担当者や日付を補っていません。結果画面を閉じても実行は取り消されないため、再実行前に履歴を確認します。

## Step 4. 公開版を作り、利用者の入口で確認する

**目標：** 下書きの確認後に公開し、利用者の実行結果を確認します。

1. Step 3で期待と異なる場合は、最初に異なったノードだけを修正し、再度テストします。
2. 内容を確認できたら**「公開」**を選び、対象と変更内容を確認して公開を確定します。
3. 状態が公開済みになったことを確認します。
4. AppまたはProjectの利用者用入口から対象を開き、同じ日報で1回だけ実行します。
5. 結果と実行履歴を確認し、下書きと同じ観点で内容を照合します。

公開は[Workflowを公開する](../build/publish-workflow.md)、利用者としての実行は[公開済みWorkflowを実行する](../use/run-published-workflow.md)を参照してください。**確認ポイント：** 公開済みであることと、期待する結果であることは別です。利用者の入口で結果を確認します。

## よくある誤解

| 誤解 | 確認すること |
|---|---|
| ノードを線でつなげば値も渡る | 入力参照と終了出力をそれぞれ設定します。 |
| 下書きの成功は公開版の成功を示す | 公開後は利用者の入口からもう一度確認します。 |
| 回答が自然なら正しい | 入力原文と、要確認事項・予定・数値を照合します。 |
| 実行画面を閉じれば実行は消える | 実行履歴で状態と結果を確認します。 |

## うまくいかない場合

| 状況 | 最初に確認すること |
|---|---|
| LLMへ日報が渡らない | 接続だけでなく、開始ノードの入力参照を候補から入れたか確認します。[Workflowの変数・分岐を設定する](../build/configure-workflow-variables-and-branches.md)を参照します。 |
| 結果が空・想定と異なる | 終了出力、LLMの入出力、実行詳細を順に確認します。[Workflowの下書きをテストする](../build/test-workflow-drafts.md)を参照します。 |
| 公開できない・項目がない | チェックリスト、対象Project、権限、提供条件を確認します。[Workflowを公開する](../build/publish-workflow.md)を参照します。 |
| 実行結果を確認できない | 実行履歴で開始時刻、状態、入力、各ステップを確認します。[Workflowの実行履歴でデバッグする](../build/debug-workflow-run-history.md)を参照します。 |

## 後片付け

1. 実習用Workflowを残す場合は、名前と説明に実習用であることを残し、利用者へ実業務に使わないよう伝えます。
2. 不要な場合は、公開中のWorkflowであること、参照中のApp・Page・スケジュール・トリガーがないことを確認してから整理します。削除・引き継ぎの判断は[削除・引き継ぎと監査記録を確認する](../operations/deletion-handover-and-audit-logs.md)を参照してください。
3. この実習ではトリガーとスケジュールを作成しません。途中で追加した場合は、停止・無効化を確認してからWorkflowを整理します。
