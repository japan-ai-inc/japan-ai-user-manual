# 定期実行を変更・停止・引き継ぐ

Studio Projectのタスクスケジューラで設定した定期実行と、Workflowの開始ノードで設定したイベント起動は、担当者が画面を開いていない間も処理を開始できます。目的変更、認証失効、担当者交代では、対象を確認して変更・停止・引き継ぎます。

新規作成は[タスクスケジューラを設定する](../build/configure-task-scheduler.md)、イベント起動の設定は[Workflowトリガーを設定する](../build/configure-workflow-triggers.md)を参照してください。

## この記事の範囲

| 種類 | 起動のきっかけ | 主な確認場所 |
|---|---|---|
| Projectのタスク | 日時、繰り返し、またはWorkflowを対象とするWebhook | Project設定のタスクスケジューラにあるタスク一覧と履歴 |
| Workflowのイベント起動 | Webhook、メール受信、データやファイルの変化など | 対象Workflowの開始ノード、公開状態、実行履歴 |

Projectのタスクを編集・削除する操作と、Workflowの開始ノードを変更して公開する操作は別です。Workflowの開始ノードだけを下書きで変更しても、公開中のイベント起動は変わりません。

## 始める前に

- 組織、Project、App、実行対象、外部への送信・更新先、通知先を確認します。
- 変更・停止に必要なProject権限を確認します。
- 影響が大きい処理では、停止時刻、再開条件、確認者、連絡先を決めます。
- 接続や認証が関係する場合は、認証アカウントと共有・個人接続を確認します。

## 1. 稼働中の自動実行を棚卸しする

### Projectのタスクを確認する

1. 対象Projectの設定で**「タスクスケジューラ」**を開き、**「タスク一覧」**で対象を探します。
2. タスク名、実行対象、起動方法、状態、作成者、通知先を確認します。
3. 日時実行では、実行日時、繰り返し、終了日を記録します。
4. **「履歴」**で、直近の成功・失敗、日時、エラー、実行結果を確認します。

### Workflowのイベント起動を確認する

1. 対象Workflowを開き、開始ノードにイベント起動があるかを確認します。
2. イベントの種類、対象、絞り込み条件、外部アカウントの接続状態を確認します。
3. Workflowが公開済みかを確認します。
4. 実行履歴で、想定したイベントで起動しているか、重複や連続した失敗がないかを確認します。

Webhook URLや受信アドレスは外部から起動できる情報です。棚卸し表や問い合わせに必要以上に転記せず、共有範囲を限定してください。

## 2. Projectのタスクを変更する

タスク一覧で対象を編集し、名前、実行対象、入力、通知先、日時・繰り返し、終了日を見直します。

1. 変更前に、実行対象、入力、通知先、直近の実行日時を記録します。
2. 変更中に予定された実行がある場合は、直近の実行日時と変更作業が重ならないようにします。
3. 変更する項目を編集します。日時・繰り返しを変える場合は、実行日、時刻、繰り返し、終了日をまとめて確認します。
4. 保存後に、状態、実行日時、通知先を再確認します。
5. 影響を抑えた条件で実行結果を確認し、必要に応じて外部サービス側の結果も確認します。

Agent／Workflowの種類と、スケジュール／Webhookなどの起動方法は、作成後には切り替えられません。別の種類や起動方法へ切り替える場合は、対象の入力・接続・通知を確認してから新しいタスクを作成し、旧タスクとの重複実行を防ぎます。Workflowの構成を変更した場合は、テスト後に公開します。

## 3. 停止するときに確認すること

### Projectのタスク

Studio Projectのタスクスケジューラでは、既存タスクを一時停止・再開する画面操作は確認できていません。予定実行を止める必要がある場合は、削除前に影響範囲、代替手順、履歴を残す必要、Webhookの呼び出し元、通知の受信者を確認してください。タスクの削除は対象のAgentやWorkflow自体を削除する操作ではありません。

### Workflowのイベント起動

Workflowのイベント起動を止める場合は、対象Workflowの開始ノードを変更または削除して公開します。下書きだけを変更しても、公開中のイベント起動は停止しません。

## 4. 担当者交代時に引き継ぐ

タスクやWorkflowのイベント起動は、作成者・公開者や、その人の接続に依存する場合があります。交代前に、対象と外部アカウントを棚卸しします。

1. Projectのタスク一覧で、対象のタスクと作成者を確認します。Workflowのイベント起動で使う外部アカウントも確認します。
2. 目的、実行対象、入力、日時・条件、通知先、接続、直近の履歴を記録します。
3. 後任者に必要なProject・Workflow・外部サービスの権限を用意します。前任者の個人接続を引き続き使える前提にしません。
4. 後任者の設定で新しいタスクまたは接続を準備します。旧タスクと同時に実行されないよう確認します。
5. 影響を抑えた条件で実行し、履歴、通知、外部サービス側の結果を確認します。
6. 新しい設定が安定して動くことを確認した後、旧タスクを削除するか、必要な設定・履歴を別途記録として残すかを決めます。
7. Workflowのイベント起動は、後任者の接続、対象条件、公開状態を別途確認し、変更時はテスト後に公開します。

## 5. 失敗が繰り返される場合

1. 影響がある場合は、Projectのタスクの削除による影響を確認するか、Workflowのイベント起動を変更して公開し、新しい起動を止めます。
2. タスクの**「履歴」**またはWorkflowの実行履歴で、失敗日時、対象、表示メッセージ、直近の成功、変更直後かどうかを確認します。
3. タスクの状態、実行対象、入力、接続、通知先、Workflowの公開状態を確認します。
4. 外部サービス側の権限と対象データを確認します。
5. Workflow内の失敗は、実行履歴でノード、入力、出力、エラーを確認します。
6. 修正後は対象を限定して確認し、成功、通知、外部サービス側の結果を照合してから再開します。

- [ ] 変更・停止による外部処理と通知先への影響を記録した
- [ ] Projectのタスクを削除する前に、影響範囲と必要な履歴を確認した
- [ ] Workflowのイベント起動を変更・停止した場合は公開した
- [ ] 担当者交代では、Project権限、接続、外部サービス側の権限を確認した
