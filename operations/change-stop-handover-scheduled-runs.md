# 定期実行を変更・停止・引き継ぐ

Studio Projectのタスクスケジューラで設定した定期実行と、Workflowの開始ノードで設定したイベント起動は、担当者が画面を開いていない間も処理を開始できます。目的変更、認証失効、担当者交代では、対象を確認して変更・停止・引き継ぎます。

新規作成は[タスクスケジューラを設定する](../build/configure-task-scheduler.md)、イベント起動の設定は[Workflowトリガーを設定する](../build/configure-workflow-triggers.md)を参照してください。

## 要点：誰として実行されるか

| 自動実行 | 実行主体 | 変わらないこと | 所有者が組織を離れたとき |
|---|---|---|---|
| Workflowのトリガー（開始ノードのイベント起動） | その開始ノードを最初に公開した人 | 別の人が再公開しても実行主体は引き継がれない | 自動的に無効化される |
| タスクスケジューラのタスク | タスクの作成者 | タスクを編集しても実行主体は変わらない | 自動的に無効化される |
| SDK・APIで作成した定期実行 | 使用したProject APIキーの作成者 | キーは作成者がProjectの有効メンバーである間だけ有効 | 作成者がProjectの有効メンバーでなくなると、そのキーは403エラーになる |

- 自動実行では外部サービスへの接続に**共有接続が必要**です。Workflowは共有接続だけを使います。
- 実行履歴では、トリガーや定期実行による実行に所有者の名前が表示されます。「自動実行」と表示されるのはサービスアカウントによる実行だけです。
- **一時停止の機能はありません。** 緊急に止めるときは、Workflowの「有効化」をオフにします（「3. 停止する」参照）。
- 担当者を交代するには、**トリガーノードを削除して追加し直す**か、**タスクを作り直す**必要があります。後任者が再公開・編集するだけでは実行主体は変わりません（「4. 担当者交代時に引き継ぐ」参照）。

## この記事の範囲

| 種類 | 起動のきっかけ | 主な確認場所 |
|---|---|---|
| Projectのタスク | 日時、繰り返し、またはWorkflowを対象とするWebhook | Project設定のタスクスケジューラにあるタスク一覧と履歴 |
| Workflowのイベント起動 | Webhook、メール受信、データやファイルの変化など | 対象Workflowの開始ノード、公開状態、実行履歴 |

Projectのタスクを編集・削除する操作と、Workflowの開始ノードを変更して公開する操作は別です。Workflowの開始ノードだけを下書きで変更しても、公開中のイベント起動は変わりません。

> **タスクスケジューラのWebhookタスクには認証がありません。** URLを知っていれば誰でも起動できます。WorkflowのWebhookトリガー（署名検証あり）とは別の仕組みです。WebhookタスクのURLは、パスワードと同じように扱ってください。

## 始める前に

- 組織、Project、App、実行対象、外部への送信・更新先、通知先を確認します。
- 変更・停止に必要なProject権限を確認します。
- 影響が大きい処理では、停止時刻、再開条件、確認者、連絡先を決めます。
- 接続や認証が関係する場合は、共有接続とその認証アカウントを確認します。

## 1. 稼働中の自動実行を棚卸しする

### Projectのタスクを確認する

1. 対象Projectの設定で**「タスクスケジューラ」**を開き、**「タスク一覧」**で対象を探します。
2. タスク名、実行対象、起動方法、状態、作成者、通知先を確認します。作成者が実行主体です。
3. 日時実行では、実行日時、繰り返し、終了日を記録します。
4. **「履歴」**で、直近の成功・失敗、日時、エラー、実行結果を確認します。

### Workflowのイベント起動を確認する

1. 対象Workflowを開き、開始ノードにイベント起動があるかを確認します。
2. イベントの種類、対象、絞り込み条件、使用する共有接続の状態を確認します。
3. Workflowが公開済みで、「有効化」がオンかを確認します。
4. 実行履歴で、想定したイベントで起動しているか、重複や連続した失敗がないかを確認します。実行者の欄にはトリガーの所有者（開始ノードを最初に公開した人）が表示されます。

### SDK・APIで作成した定期実行を確認する

Project APIキーを使って作成した定期実行は、そのキーの作成者として実行されます。キーの作成者と、作成者がProjectの有効メンバーであるかを確認します。キーの管理は[Project APIキーを管理する](manage-project-api-keys.md)を参照してください。

Webhook URLや受信アドレスは外部から起動できる情報です。棚卸し表や問い合わせに必要以上に転記せず、共有範囲を限定してください。

## 2. Projectのタスクを変更する

タスク一覧で対象を編集し、名前、実行対象、入力、通知先、日時・繰り返し、終了日を見直します。

1. 変更前に、実行対象、入力、通知先、直近の実行日時を記録します。
2. 変更中に予定された実行がある場合は、直近の実行日時と変更作業が重ならないようにします。
3. 変更する項目を編集します。日時・繰り返しを変える場合は、実行日、時刻、繰り返し、終了日をまとめて確認します。
4. 保存後に、状態、実行日時、通知先を再確認します。
5. 影響を抑えた条件で実行結果を確認し、必要に応じて外部サービス側の結果も確認します。

タスクを編集しても、実行主体（作成者）は変わりません。Agent／Workflowの種類と、スケジュール／Webhookなどの起動方法は、作成後には切り替えられません。別の種類や起動方法へ切り替える場合は、対象の入力・接続・通知を確認してから新しいタスクを作成し、旧タスクとの重複実行を防ぎます。Workflowの構成を変更した場合は、テスト後に公開します。

## 3. 停止する

一時停止・再開の機能はありません。止め方は対象ごとに次のとおりです。

| 対象 | 止め方 | 注意点 |
|---|---|---|
| Workflow（トリガーを含む） | Workflowの**「有効化」**をオフにする。緊急停止もこの操作で行う | Email by JAIとストレージのトリガーは削除扱いになります。Webhookトリガーを作り直すと、Webhook URLが変わります。再開時はトリガーと呼び出し元の設定を確認します |
| Workflowのイベント起動だけを止める | 開始ノードを変更または削除して公開する | 下書きだけを変更しても、公開中のイベント起動は停止しません |
| Projectのタスク | タスクを削除する | 削除前に、影響範囲、代替手順、残す必要のある履歴、Webhookの呼び出し元、通知の受信者を確認します。タスクの削除は、対象のAgentやWorkflow自体を削除する操作ではありません |

## 4. 担当者交代時に引き継ぐ

自動実行の実行主体は、後任者が再公開・編集しても変わりません。前任者が組織を離れると、その人のトリガーとタスクは自動的に無効化されます。交代前に、次の手順で後任者の実行に切り替えます。

1. Projectのタスク一覧で、対象のタスクと作成者を確認します。Workflowのトリガーと、SDK・APIで定期実行を作成したProject APIキーも洗い出します。
2. 目的、実行対象、入力、日時・条件、通知先、接続、直近の履歴を記録します。
3. 後任者に必要なProject・Workflow・外部サービスの権限を用意します。自動実行に使う共有接続が、前任者の退出後も使える業務アカウントで認証されているかを確認します。
4. 後任者が引き継ぎます。
   - **タスク**：後任者が新しいタスクを作成します。旧タスクと同時に実行されないよう、作成後に旧タスクを削除します。
   - **Workflowのトリガー**：後任者がトリガーノードを削除して追加し直し、公開します。Webhook URLとEmail by JAIの受信アドレスは新しくなるため、呼び出し元・送信元を更新します。
   - **SDK・APIで作成した定期実行**：後任者がProject APIキーを作成し、そのキーで定期実行を作り直します。
5. 影響を抑えた条件で実行し、履歴の実行者が後任者になっていること、通知、外部サービス側の結果を確認します。
6. 必要な設定・履歴を記録として残してから、前任者のProjectからの削除などを進めます。

## 5. 失敗が繰り返される場合

1. 影響がある場合は、Workflowの「有効化」をオフにするか、タスクを削除して、新しい起動を止めます。
2. タスクの**「履歴」**またはWorkflowの実行履歴で、失敗日時、対象、表示メッセージ、直近の成功、変更直後かどうかを確認します。
3. タスクの状態、実行対象、入力、共有接続、通知先、Workflowの公開状態と「有効化」を確認します。
4. 所有者（タスクの作成者、トリガーを最初に公開した人、APIキーの作成者）が組織・Projectに在籍しているかを確認します。
5. 外部サービス側の権限と対象データを確認します。
6. Workflow内の失敗は、実行履歴でノード、入力、出力、エラーを確認します。
7. 修正後は対象を限定して確認し、成功、通知、外部サービス側の結果を照合してから再開します。

## チェックリスト

- [ ] Projectのタスク一覧、履歴、Workflowの開始ノード、SDK・APIで作成した定期実行を確認した
- [ ] 各自動実行の実行主体（作成者・最初の公開者・APIキー作成者）を記録した
- [ ] 変更・停止による外部処理と通知先への影響を記録した
- [ ] WebhookタスクのURLを必要以上に共有していない
- [ ] 緊急停止は「有効化」のオフで行い、再開時にトリガーの設定を確認した
- [ ] 担当者交代では、トリガーノードの追加し直し、またはタスクの作り直しを行った
- [ ] 再開後に履歴、通知、外部サービス側の結果を確認した
