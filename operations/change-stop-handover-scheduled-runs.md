# 定期実行を変更・停止・引き継ぐ

定期実行やWorkflowトリガーは、担当者が画面を開いていない間も処理を起動します。目的変更、認証失効、担当者の異動・退職時は、自動実行を特定して変更・停止・引き継ぎます。

この記事では、運用担当者がタスクとWorkflowトリガーを棚卸しし、変更・停止・失敗対応・担当交代を行う手順を説明します。新規作成の手順は[タスクスケジューラを設定する](../build/configure-task-scheduler.md)、イベントトリガーの設定は[Workflowトリガーを設定する](../build/configure-workflow-triggers.md)を参照してください。

## この記事の範囲

ここでいう自動実行は、次の二つです。

| 種類 | 起動のきっかけ | 主な確認場所 |
|---|---|---|
| タスク | 日時・繰り返し・Webhookなど | **「タスク」**の「使っているもの」のタスク、タスク詳細の「次回実行」「履歴」 |
| Workflowトリガー | Webhook、JAIメール、メール受信、データやファイルの変化など | 対象Workflowの開始ノード、公開状態、実行履歴 |

自動実行は、**タスクとして作成・設定したトリガー**と、**Workflow自身が公開時に作成・管理するトリガー**を分けて確認します。前者は「タスク」で無効化・設定変更します。後者はWorkflowを公開すると更新されるため、通常のタスク設定では変更できず、開始ノードを変更して公開します。

Workflow自身のトリガーを「タスク」から削除できる表示でも、削除できるのは自分の公開者トリガーを削除できる条件を満たす場合だけです。他のメンバーが利用している、または現在のWorkflow版からタスクを作成できない場合は削除できず、次回の公開で元に戻る場合があります。Workflowの下書きだけを変えても、公開中のトリガーは停止しません。

> 自動実行には、メール送信や外部サービスの更新が含まれることがあります。障害・誤実行・担当交代時は、次回の実行またはイベント起動を止める判断をします。結果が不明なまま「今すぐ実行」や再実行を繰り返さないでください。

## 始める前に

- 組織、Project、Appを確認します。同名の対象や本番・検証用の対象を取り違えないでください。
- 変更対象の業務目的、実行対象のAgentまたはWorkflow、外部への送信・更新先、通知先、作成者、管理担当者を確認します。
- 変更・停止の権限を確認します。
- 影響が大きい処理は、連絡先、停止時刻、再開条件、確認者を決めます。
- 接続や認証が関係する場合は、認証アカウントと共有・個人接続を確認します。接続の失効や担当者変更の対応は[接続の失効・担当者変更に対応する](handle-expired-connections-and-owner-changes.md)を参照してください。

## 1. 稼働中の自動実行を棚卸しする

変更・退職者の処理前に、対象の自動実行を一覧化します。名前だけでなく、起動条件と直近の結果を確認します。

### タスクを確認する

1. ナビゲーションの**「タスク」**を開き、**「使っているもの」**で対象のタスクを探します。Workflowと従来のタスクスケジューラーは、この「タスク」画面に統合されています。以前の画面を開いた場合は、表示される案内に従って「タスク」へ移動します。
2. タスクのカードまたは詳細で、タスク名、説明、実行対象、トリガー、状態、作成者を確認します。必要に応じて、対象部門名や業務名で照合します。
3. 各タスクを開き、**「次回実行」**、通知先、実行時間、繰り返し、終了日を記録します。
4. **「実行履歴」**で、最新の成功・失敗、発生日時、表示されたエラー、実行結果を確認します。Workflowを実行するタスクは、必要に応じて[Workflowの実行履歴でデバッグする](../build/debug-workflow-run-history.md)も確認します。

### Workflowトリガーを確認する

1. 自動実行の可能性があるWorkflowを開き、開始ノードにトリガーがあるかを確認します。
2. トリガーの種類、対象データ・メール・フォルダー、絞り込み条件、外部アカウントの連携状態を確認します。
3. Workflowが公開済みか、開始ノードが受信中などの有効な状態かを確認します。
4. 実行履歴で、想定したイベントで起動しているか、重複や連続した失敗がないかを確認します。

> Webhook URLや受信アドレスは、外部から起動できる情報です。棚卸し表や問い合わせに必要以上に転記せず、共有範囲を限定してください。認証情報、メール本文、個人情報を実行履歴からそのまま転記しないでください。

## 2. タスクの設定を変更する

タスク名、説明、プロンプト、通知先、スケジュール、終了日などは、対象タスクの**「タスクの更新」**から見直せます。変更前に、直後の実行と外部処理への影響を確認します。

1. 対象タスクの「実行対象」「実行方法」「通知先」「次回実行」を記録します。
2. 変更中に予定されている実行を確認し、必要なら先に無効にします。
3. **「タスクの更新」**を開き、変更する項目だけを見直します。スケジュールを変える場合は、実行日・時刻・繰り返し・終了日をまとめて確認します。
4. **「更新」**後に、状態、**「次回実行」**、通知先を再表示して確認します。
5. 影響を抑えた条件で最初の結果を確認し、必要に応じて外部サービス側の送信先・更新先も確認します。

トリガーの種類とWorkflow由来の実行対象は、既存タスクの更新で変更できません。Agentタスクでは、画面に選択肢があり権限もある場合に、Agentやモデルを変更できることがあります。別の起動方法またはWorkflowへ変える場合は、新しいタスクを作成し、テストと通知設定の確認後に旧タスクを停止します。Workflowを変更した場合は、公開済みの版が実行されるため、Workflow側の修正・テスト・公開も必要です。

## 3. 一時停止・完全停止を使い分ける

### 一時的に止める

原因調査、認証の修復、業務の休止、引き継ぎの準備中は、タスクを**「無効」**にします。無効のままでは、実行時刻を設定しても実行されません。再開時は、設定・接続・通知先・次回実行を確認してから有効に戻します。

既に開始した実行は別途確認します。外部送信・更新を含む場合は、履歴と外部サービスの結果を確認し、重複実行の要否を判断してください。

Workflowトリガーを止める場合は、対象Workflowで開始ノードを変更または削除し、**公開**します。下書きで開始ノードを削除しただけでは、公開中のトリガーは停止しません。停止後は、想定外のイベントで新しい実行履歴が増えていないことを確認します。

### 不要になったタスクを削除する

業務の終了などで再開する予定がなく、履歴と設定を残す必要がないことを確認した場合にのみ、**「タスクの削除」**から**「削除」**します。この操作は元に戻せません。削除前に、代替タスク、Webhookの呼び出し元、通知の受信者、業務手順を確認します。

> 「タスクの削除」は、実行対象のAgentやWorkflow自体を削除する操作ではありません。一方、外部システムがWebhook URLを呼び出し続ける、または別のWorkflowトリガーが残る可能性があります。自動実行全体を止めたいときは、関連するタスクと開始ノードを両方確認してください。

## 4. 担当者の異動・退職時に引き継ぐ

タスクとWorkflowトリガーは、作成・公開したメンバーや、そのメンバーの認証情報に依存する場合があります。メンバーが組織を離れると、そのメンバーが作成したタスク、およびそのメンバーの認証情報を使うトリガーは無効化されます。退職処理の後に初めて失敗に気付くのではなく、前もって棚卸しします。

通常のタスク更新で作成者を変更できることは確認できません。引き継ぎは、後任者が新しいタスクを作成して切り替える方法を基本にします。

1. 異動・退職予定者について、「タスク」の「使っているもの」で**「作成者」**を確認し、Workflowトリガーで利用する外部アカウントと照合します。
2. 目的、実行対象、入力、スケジュール・条件、通知先、接続、直近の履歴を記録します。
3. 後任者に必要な組織・Project・Workflowの権限と、外部サービス側の権限を準備します。前任者の個人接続を後任者が使える前提にしません。
4. 後任者が新しいタスクを作成します。既存タスクと同時に動かないよう、旧タスクを無効にしてから、実行対象・入力・スケジュール・通知先を確認します。
5. 後任者の権限と接続で安全な条件で実行し、履歴、通知、外部サービス側の結果を確認します。
6. 新しいタスクが安定して動くことを確認した後、旧タスクを削除するか、無効のまま記録を保持するかを決めます。
7. Workflowトリガーは、後任者の接続、対象条件、公開状態を別途確認します。公開者や認証アカウントの変更が必要な場合は、既存の開始ノードを推測で再利用せず、[Workflowトリガーを設定する](../build/configure-workflow-triggers.md)と[接続の失効・担当者変更に対応する](handle-expired-connections-and-owner-changes.md)に従って確認・公開します。

退職処理後は、対象者に関係するタスク・トリガーが無効になっていること、予定されていた実行が継続していないこと、後任の自動実行だけが動いていることを確認します。

## 5. 失敗が繰り返される場合

同じ失敗が続くと、通知の見落としや重複処理につながる可能性があります。エラーだけを見て設定を連続変更せず、次の順で切り分けます。

1. 影響がある場合は、対象タスクを無効にするか、Workflowトリガーを停止・公開して、新しい起動を止めます。
2. **「実行履歴」**で失敗した日時、対象、表示メッセージ、成功していた最終時刻、変更直後かどうかを確認します。
3. タスクが無効でないか、作成者が組織のメンバーか、実行対象のAgent・Workflowが利用可能か、Workflowが公開済みかを確認します。
4. 接続・認証、外部サービス側の権限、対象データ、通知先を確認します。認証の問題は[接続の失効・担当者変更に対応する](handle-expired-connections-and-owner-changes.md)を参照してください。
5. Workflow内の失敗は、実行履歴でノード、入力、出力、エラーを確認します。起動・入力・ノード失敗の詳細な切り分けは[Workflowが起動しない・失敗する](../troubleshooting/workflow-not-starting-or-failing.md)で扱います。
6. 修正後は対象を限定して確認し、成功、通知、外部サービス側の結果を照合してから再開します。

| 状況 | 確認・対応 |
|---|---|
| タスクが実行されない | 状態が「有効」か、「次回実行」が意図どおりか、終了日を過ぎていないかを確認します。 |
| 「タスクの作成者が組織のメンバーではないため実行されませんでした。」 | 作成者の離脱が原因です。無効化された旧タスクを前提にせず、後任者が新しいタスクを作成して確認します。 |
| Workflowが起動しない | 公開状態、開始ノード、イベント条件、接続状態を確認します。下書きだけの変更では停止・変更になりません。 |
| 接続・認証に関する失敗 | 個人接続か共有接続か、認証アカウント、外部サービス側の権限を分けて確認します。 |
| 実行結果は成功でも業務結果が違う | プロンプト・入力・公開済みWorkflow・送信先／更新先を確認し、履歴だけで完了と判断しません。 |

## チェックリスト

- [ ] 「タスク」の「使っているもの」の一覧、次回実行、実行履歴、Workflowの開始ノードを確認した
- [ ] 変更・停止する自動実行と、外部処理・通知先への影響を記録した
- [ ] 一時停止は「無効」、不要なタスクだけを「削除」と使い分けた
- [ ] Workflowトリガーの変更・停止後に公開した
- [ ] 担当交代では、前任者の作成タスクと認証に依存するトリガーを確認した
- [ ] 後任者の権限・接続で新しいタスクまたはトリガーを確認した
- [ ] 失敗が続く自動実行は、原因確認前に実行を繰り返していない
- [ ] 再開後に履歴、通知、外部サービス側の結果を確認した
