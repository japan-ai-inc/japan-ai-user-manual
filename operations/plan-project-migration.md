# Project間の移行を計画する

Projectを切り替えるときは、一括移行を前提にせず、リソースごとに**リンクする・移行先で作り直す・Appとして公開してインストールする**のどれにするかを決めます。同名のAgentやWorkflowを作るだけでは、Dataset、Skill、接続、Secret、Storage、Page、Objectなどの依存先はそろいません。

この記事では、移行前の棚卸しと確認順を説明します。リンクの操作と解除は[既存リソースをリンク・解除する](../build/link-and-unlink-resources.md)、Pageの設計は[配布可能なPageの設定設計](../development/design-distributable-page-config.md)、配布時の制約は[配布対象・依存・認証設定の制約](../distribution/distribution-scope-dependencies-auth.md)を参照してください。

## 要点

| 項目 | 決まり |
|---|---|
| Project間のコピー | **機能はありません。** |
| リンクできるもの | **組織レベルのリソースと公式のリソースのみ**です（Agent、Workflow、ナレッジ（Datasetを含む）、Skill）。別のProject内で作ったリソースはリンクできません。 |
| Project内で作ったリソースを移す方法 | 移行先で作り直すか、Appとして公開してからインストールします。 |
| リンクの性質 | 同じリソースを参照します。元の変更はリンク先すべてに即時に反映されます。Agentのリンクを解除すると、そのAgentのIAMの割り当ても消えます。 |

## この記事の範囲

ここでいう移行は、同じ組織内で構成とデータを移すための計画です。Projectの削除、外部サービス側のデータ移管、認証情報の値の受け渡しは扱いません。Appの公開・インストールの手順は[配布対象・依存・認証設定の制約](../distribution/distribution-scope-dependencies-auth.md)から各ページを参照してください。

「リソースを追加」でリンクできるのは、組織レベルまたは公式の**エージェント、ワークフロー、ナレッジ（Datasetを含む）、スキル**です。Object、Storage、Page、コネクタ、Project Secretはリンクできません。

> リンクは元のリソースそのものへの参照です。移行先だけで独立して変更したい場合、リンクでは実現できません。

## 移行方式を先に選ぶ

各対象について、次のどれにするかを記録します。

| 方式 | 使える対象 | 元との関係 | 移行後に確認すること |
|---|---|---|---|
| リンク | 組織レベル・公式のAgent、Workflow、ナレッジ、Skill | 同じリソースを参照する。元の変更はリンク先すべてに即時に反映される | 元の管理者・更新手順を明確にする |
| 作り直し | すべて（Project内で作ったリソースを含む） | 移行先に新しい設定・データを用意する。元とは独立する | 元と移行先を照合し、切替後の実行結果を確認する |
| Appとして公開・インストール | 元Projectで作ったAgent、Workflow、Page など、Appの公開対象になるもの | Appとして導入される。公開に含まれる範囲は配布の仕様に従う | 公開できない構成がないか、インストール後の初期設定（共有接続・Secret）を確認する |

## 対象別の移行方針

| 対象 | 方針 | 主な確認 |
|---|---|---|
| Agent | 組織・公式のものはリンク。Project内で作ったものは作り直すか、App経由で移す。 | 指示、モデル、Dataset・Skill・接続、既定Agent。 |
| Workflow | 組織・公式のものはリンク。Project内で作ったものは作り直すか、App経由で移す。 | テスト・公開、開始条件、実行主体、実行先。 |
| Dataset | 組織・公式のものはナレッジとしてリンク。それ以外は取り込み直す。 | 共有範囲、処理状態、参照設定。 |
| Skill | 組織・公式のものはリンク。Project内で作ったものは作り直す。 | 添付ファイル、公開範囲、Agentへの追加。 |
| Object | 移行先で構造を作り直し、必要なレコードを移す。 | フィールド、アクセス条件、リレーション、取込結果。参照先から先に用意する。 |
| Storage | 移行先にフォルダとファイルを用意する。 | 構成、権限、Agent・Workflow・Pageのパス。 |
| Page | 移行先でPageのソースをアップロードし直す。 | アクセス条件、Storage参照、Secret名。 |
| コネクタ | 移行先で選択・作成・認証する。 | 認証アカウント、個人／共有。Workflowは共有接続のみを使う。 |
| Project Secret | 移行先で新規登録する。 | 実値は記録せず、代表操作を確認する。 |
| Project APIキー | 移行先で新しく発行する。 | キーは作成者として動作する。外部システムの設定を切り替える。 |

> 認証情報とSecretは、設定名だけを移す対象ではありません。移行先の外部サービス権限、認証アカウント、共有範囲、実行結果を確認して初めて切替完了と判断します。値そのものを移行用の表や問い合わせに記載しないでください。

## 1. 移行台帳を作る

元Projectを変更する前に、対象を一覧化します。画面の一覧だけでなく、Agent・Workflow・Pageが参照する先も確認します。

| 台帳に記録する項目 | 記録例 |
|---|---|
| 対象 | Agent、Workflow、Dataset、Skill、Object、Storage、Page、コネクタ、Project Secret、APIキー |
| 名前と用途 | 一覧で判別できる名称、業務上の利用目的 |
| 移行方式 | リンク、作り直し、App経由、移行不要 |
| 元・移行先 | 元Project、移行先Project、元の管理者 |
| 依存関係 | Agent→Skill／Dataset、Workflow→Agent／Skill、Page→Storage／接続など |
| 責任者・確認方法 | 内容確認者、認証者、代表操作、切替承認者 |
| 切替・戻し方 | 切替日時、旧構成を残す期間、連絡先 |

外部サービスへ送信・更新するWorkflow、定期実行、Webhook、公開中のPage、共有接続、Secretは影響がある対象として記録します。

## 2. 依存関係を元から外へたどる

移行対象を単位ごとに確定します。

1. Agentごとに、「プラグイン」「データ連携」、モデル、指示、利用対象者を記録します。
2. Workflowごとに、利用するAgent、Workflow、Skill、Dataset、開始条件、入力、公開状態、実行先を記録します。
3. Workflowをリンクする場合は、確認画面の**「依存リソースの自動追加」**と**「スキップされた依存リソース」**を確認します。必要なAgent・Workflow・Skillが自動追加されることがあります。
4. Object、Storage、Pageについて、名前だけでなく、参照先のObject、ファイルパス、接続・Secret名を記録します。
5. コネクタとProject Secretについて、実値を書かずに、用途、認証担当者、接続先、参照する機能、更新時の連絡先を記録します。

「スキップされた依存リソース」には、アクセス権限不足、見つからない、無効、削除済み、Project固有、スコープ外などの理由が表示されます。Project固有のものはリンクできないため、移行先で作り直します。

## 3. 依存先から順に移行する

利用する定義より先に、その定義が参照するデータ・認証・設定を用意します。

1. 移行先Projectのメンバー、役割、移行担当者、テスト用のデータと外部サービスの検証先を決めます。
2. Objectの構造と必要なレコード、Storageのフォルダとファイルを移行先に用意します。
3. コネクタとProject Secretを移行先で設定し、外部サービスの最小限の代表操作を確認します。
4. DatasetとSkillをリンクまたは作り直し、共有範囲と利用可否を確認します。
5. Agentをリンクまたは作り直し、移行先のDataset・Skill・接続の前提が満たされることを確認します。
6. Workflowをリンクまたは作り直します。依存リソースの自動追加・スキップを確認し、作り直したものはテスト後に公開します。
7. Pageを移行先へアップロードし、Storage参照、認証、Pageの表示と代表操作を確認します。
8. 定期実行、Webhook、通知など、実行を重複させるおそれのある設定を最後に切り替えます。

> 元Projectと移行先Projectの両方で自動実行を有効にすると、同じ通知、送信、更新が重複します。切替時刻、旧構成を停止する担当者を決めてから有効化してください。

## 4. 切替前後を照合する

移行先で設定が見えることと、利用者の操作が成功することを分けて確認します。

### 移行前チェックリスト

- [ ] 元・移行先のProject、管理者、切替日時、戻し方を記録した
- [ ] 対象をAgent、Workflow、Dataset、Skill、Object、Storage、Page、コネクタ、Project Secret、APIキーに分けて棚卸しした
- [ ] 各対象をリンク・作り直し・App経由・移行不要に分類した（リンクは組織レベル・公式のリソースのみ）
- [ ] Workflowの依存リソース、自動追加、スキップ理由を確認した
- [ ] 外部送信、データ更新、定期実行、Webhook、公開Pageを影響ありとして確認した
- [ ] Secret値やトークンを台帳へ記録していない

### 切替後チェックリスト

- [ ] リンクしたリソースの更新担当（元の管理者）を確認した
- [ ] 作り直したリソースで、必要な変更を移行先で行えることを確認した
- [ ] Datasetの処理状態、Skillの公開範囲、Objectの構造・レコード、Storageのファイルを確認した
- [ ] Agent、Workflow、Pageの代表操作を、許可されたテストデータで確認した
- [ ] 外部サービス側で送信先・更新先・実行アカウントが正しいことを確認した
- [ ] 旧Projectの自動実行・Webhook・利用案内を整理し、重複実行しないことを確認した
- [ ] 旧構成を削除する前に、移行先の運用担当者が確認を完了した

## うまくいかない場合

リンクの候補に出ないリソース（Project内で作ったもの、Object、Storage、Page、コネクタ、Secret）は、作り直すかApp経由で移します。

管理者または担当者へ相談するときは、次を記録します。

1. 元・移行先の組織とProject、対象種別・名称、利用目的。
2. 選んだ移行方式、画面に表示された候補・スキップ理由・エラーメッセージ。
3. 依存するAgent、Workflow、Dataset、Skill、Object、Storage、Page、接続、Secret名。
4. 外部送信・更新の有無、切替希望時刻、すでに実施したテスト結果。

Secret値、APIキー、トークン、パスワード、機密データ、不要なファイル本文は問い合わせに含めません。
