# App更新の変更点と再設定を確認する

Appの更新では、画面や機能だけでなく、必要な接続、Secret、業務の操作手順が変わる場合があります。この記事では、**導入済みAppの変更点を確認し、必要な再設定と動作確認を終えるまでの進め方**を説明します。

**「新しい版が公開された」「自分の組織へ反映された」「業務で使えることを確認した」は、別の状態です。** Marketplaceの案内やバージョン表示だけで、更新後の利用準備まで完了したとは判断しないでください。

この記事の対象は、導入先のApp管理者です。作成者による組織内self-installの更新操作、リリースの審査・配布、互換性の管理は配布担当者向けの記事で扱います。

## 始める前に

- 対象の組織・App・提供元を確認します。
- 更新案内がある場合は、変更内容、対象バージョン、導入先への反映状況を確認します。
- 業務で使っている機能と、影響を受ける利用者を整理します。
- 共通接続・Secretを設定できる担当者と、利用継続を判断する担当者を確認します。
- 動作確認に使うデータと、実行してよい操作を決めます。

> 画面の表示や操作範囲は、組織の設定・権限・Appの構成によって異なります。以下は確認の順序です。全Appに共通する「更新」ボタンや、利用者が必ず更新を承認する画面があることを前提にはしていません。

初期設定がまだ終わっていない場合は、先に[Appの初期設定を完了する](complete-app-setup.md)を確認してください。

## 1. 更新の案内と、導入先の状態を分けて確認する

### 更新内容を確認する

Marketplaceの詳細画面に「新機能」や変更内容が表示される場合は、対象バージョンとともに読みます。掲載内容だけで変更点が分からない場合は、提供元や配布担当者へ確認してください。

特に、次の変更が業務に関係するかを確認します。

| 変更の種類 | 確認すること |
|---|---|
| 画面・操作手順 | 入口、入力項目、実行ボタン、結果の確認方法が変わるか |
| Agent・Workflow | 入力条件、出力、実行する処理、外部サービスへの操作が変わるか |
| 接続・認証 | 接続先サービス、利用アカウント、必要な許可、個人用／共通の使い分けが変わるか |
| Project Secret | 新しい項目や、値・割り当ての見直しが必要か |
| データ・ファイル | 入出力の形式、保存先、既存データの扱いに変更があるか |
| 運用 | 自動実行、通知、利用者への案内に変更があるか |

これは影響確認の観点です。すべての更新で、これらが変更されるわけではありません。

### 導入済みAppの状態を確認する

1. 正しい組織で、導入済みの対象Appを開きます。
2. Appの説明欄などにバージョンやインストール状態が表示される場合は、内容を確認します。
3. 更新案内の対象と、導入先に表示されている版を照合します。
4. 表示がない、版が異なる、反映済みか判断できない場合は、配布担当者に対象組織への反映状況を確認します。

**Marketplaceに掲載されている版と、導入先で有効になっている版を混同しないでください。** Appの状態が「有効」でも、それだけでは期待する最新版への更新完了を示しません。

### 自動更新でも確認を省略しない

組織内self-install以外の導入済みAppでは、提供元の安定版への切り替えに伴い、配布条件を満たした導入先へ自動的に更新が配布される場合があります。ただし、新しい版の公開と、すべての導入先での反映完了が同時になるとは限りません。

組織内self-installはこの自動配布の対象外です。作成者側の更新操作は、[組織内self-installを更新する](../distribution/update-self-install.md)で扱います。

更新が見当たらない場合も、最初からインストールし直したり、別のAppを追加したりせず、現在の導入状態と更新対象を確認してください。

## 2. 業務への影響と確認担当を整理する

変更案内を読んだら、自分たちの業務で確認する項目に置き換えます。変更内容が不明な項目は「影響なし」ではなく「未確認」として残します。

| 確認項目 | 記録する内容 |
|---|---|
| 対象の業務・機能 | どのPage、Agent、Workflowなどを使っているか |
| 想定される影響 | 操作変更、接続追加、入力形式の変更など |
| 確認担当 | App管理者、接続管理者、利用者本人など |
| 確認方法 | どのデータで何を実行し、何を成功とするか |
| 利用判断 | 確認済み、確認待ち、一部利用見合わせなど |

更新前の状態が分かる場合は、利用バージョン、接続の名前・種類、通常の処理結果を記録しておくと比較しやすくなります。すでに更新された後であれば、分かる範囲の情報から確認を進めてください。

記録するのは設定項目や状態であり、APIキー、パスワード、Secretの値ではありません。また、確認用の記録を残すことは、元の版へ戻せることの保証にはなりません。

## 3. 更新後の接続・Secretを確認する

Appを開き直し、「要設定」「設定を確認」などの案内と、App設定の「コネクタ」「シークレット管理」を確認します。

更新のたびにすべての認証をやり直すのではなく、**現在の要件と状態に基づいて、必要な項目だけ対応**してください。反対に、以前使えていたことだけを理由に、更新後も設定確認が不要とは判断しないでください。

### App共通の接続

- Appが必要とする接続に、未設定・無効などの項目がないか
- 接続先のサービス、アカウント、組織が意図したものか
- 新しい許可を求められる場合、その範囲と用途が承認されているか
- 接続を作成・変更しただけでなく、Appへの割り当てが完了しているか

管理権限がない場合は、接続を管理できる担当者へ依頼します。設定操作は[Project・Appの共有接続を設定する](../operations/configure-shared-connections.md)、失効や担当者変更への対応は[接続の失効・担当者変更に対応する](../operations/handle-expired-connections-and-owner-changes.md)で扱います。

### 利用者本人の接続

個人用の接続が必要なAppでは、利用者本人の状態も確認します。管理者の接続が動いていても、他の利用者が認証済みとは限りません。

本人の接続や追加の許可が必要な場合は、対象となる利用者へ案内します。管理者のアカウントや秘密情報を配って代用しないでください。具体的な操作は[自分の外部アカウントを接続する](../operations/connect-your-external-accounts.md)で扱います。

### Project Secret

- Appが必要とするSecretの項目を確認します。
- 新しい項目や未設定の項目がある場合は、担当者が必要な値と用途を確認します。
- 保存先のSecretと、Appが参照する項目への紐づけを確認します。
- 設定後に状態を再取得し、未設定や無効が残っていないか確認します。

Project SecretとWebログイン用シークレットは別の設定です。同じ名前に見えても、目的の異なる種類や別環境の値を使用しないでください。登録・更新の操作は[Project Secretを登録・更新・削除する](../operations/manage-project-secrets.md)で扱います。

### 設定状態の読み方

| 表示・状態 | 対応 |
|---|---|
| 未設定 | 必要な接続・Secretと割り当て先を確認する |
| 確認中 | 判定が終わってから再確認する |
| 無効・停止中 | 対象項目と案内を確認し、担当者へ対応を依頼する |
| 設定済み・接続済み | 設定状態の確認後、必要な業務操作を試す |
| 設定確認不可・読み込み失敗 | 設定不要とは判断せず、再表示や担当者への確認を行う |

共有設定の完了表示は、全利用者の個人認証や、外部サービスでの処理成功まで保証するものではありません。

## 4. 普段の業務を、許可された範囲で確認する

変更された機能に加え、日常的に使う重要な操作も確認します。Appの構成に応じて、次の観点から必要なものを選んでください。

| 対象 | 確認例 |
|---|---|
| Page | 画面を開けるか。入力・結果表示・画面遷移が業務上の期待どおりか |
| Agent | 必要な依頼を実行できるか。接続先、回答、成果物が適切か |
| Workflow | 想定した入力で実行できるか。処理結果と履歴を確認できるか |
| Object・Storage | 必要なデータ・ファイルへアクセスできるか。保存先が適切か |
| 外部連携 | 意図したアカウントと対象データで処理されるか |
| 自動実行・通知 | 使用している場合、更新後の実行結果や通知先を確認できるか |

**メール送信、外部データの更新、削除などを、単なる確認として無断で実行しないでください。** テスト用データや承認済みの宛先を使い、どこまで操作してよいかを先に決めます。

管理者だけでなく、必要に応じて実際の利用者にも、本人のアカウントで確認を依頼します。権限を一時的に広げて成功させるのではなく、本来の利用条件で確認してください。

実行結果が分からない場合は、履歴や保存先を確認してから再実行を判断します。画面の再読み込みと業務処理の再実行は別です。二重送信・二重登録につながる操作を繰り返さないでください。

## 5. 利用者へ変更点と残作業を伝える

確認後は、少なくとも次の内容を共有します。

- 対象Appと、確認できたバージョンまたは反映状況
- 利用者に関係する変更点
- 本人の再接続など、利用者に依頼する作業
- 動作確認が終わった機能と、まだ確認できていない機能
- 利用を見合わせる範囲がある場合は、その対象
- 問い合わせ先

「更新済みなので問題ありません」と一括で案内せず、確認できた範囲を具体的に伝えます。残作業がある場合は、担当者と利用上の注意を明確にしてください。

## うまくいかないとき

| 状況 | 最初に確認すること |
|---|---|
| Marketplaceの版と導入先の版が異なる | 対象の組織・App、導入方式、配布担当者が確認した反映状況 |
| 更新案内はあるが変更内容が分からない | 提供元の案内。情報不足を「変更なし」と判断しない |
| 更新後に要設定と表示される | 現在のコネクタ・Project Secretの要件と割り当て |
| 管理者は使えるが、利用者は使えない | 本人の接続、Appのアクセス権、外部サービス側の権限 |
| 設定済みなのに処理に失敗する | 使用アカウント、対象データ、App固有の条件、実行時エラー |
| 自動実行や通知が動かない | 接続状態、実行履歴、通知先、更新案内の運用変更 |
| 更新の失敗や反映状況が分からない | 配布担当者へ状態確認を依頼する。再インストールを先に試さない |

問い合わせには、組織名、App名、表示されているバージョン・状態、発生日時、操作内容、エラー、影響する利用者・機能を添えます。確認できなかった情報は、そのまま未確認と伝えてください。

原因を調べずに接続やSecretを削除したり、Appをアンインストールしたりしないでください。元の版へ戻す必要がある場合も、利用者側で戻せるとは限らないため、配布担当者と対応を相談します。

## 完了チェック

- [ ] 対象の組織・Appと、導入先への反映状況を確認した
- [ ] 更新案内と業務への影響を確認し、不明点を未確認として残した
- [ ] 必要な共通接続・個人接続・Project Secretを確認した
- [ ] 設定確認不可や読み込み失敗を、設定完了と取り違えていない
- [ ] 実際の利用条件と許可されたデータで、重要な業務操作を確認した
- [ ] 利用者へ変更点、必要な作業、利用可能な範囲、問い合わせ先を伝えた
