# 権限・認証エラー

操作はできるはずなのに拒否される、API／SDKで401・403が返る、外部サービスの接続が使えない、またはPageを開いた後に再認証を求められるときの切り分けです。対象は利用者・管理者です。症状が似ていても、**利用者のロール、Project APIキー、外部接続、自動実行の実行主体、Pageセッション**は別の原因です。認証情報を取り替えたり権限を広げたりする前に、どの経路で失敗したかを分けます。

## 要点：誰の権限・認証情報で動くか

| 経路 | 使われる権限・認証情報 | 押さえておくこと |
|---|---|---|
| 画面操作 | 操作した人の組織ロール、Projectロール、IAM | Projectのロールは「管理者」「編集者」「メンバー」です。閲覧者（読み取り専用）のロールはありません。読み取り専用にするにはカスタムロールが必要です。メンバーはAgentやWorkflowを実行でき、多くのリソースを作成できます。編集者はメンバーを管理できません。 |
| Project APIキー | キーのスコープと、キーの作成者 | キーは作成者がProjectの有効メンバーである間だけ有効です。作成者をProjectから外すと、その人が作ったキーはすべて403になります。スコープは作成後に変更できません。SDK／APIで作成した定期実行は、キーの作成者として実行されます。 |
| Project内のAgentの外部接続 | 実行者の個人接続 → Projectの共有接続 → 組織共通の接続の順 | 先に見つかった接続が使われます。 |
| Workflowの外部接続 | Projectの共有接続のみ | 個人接続は使われません。自動実行には共有接続の設定が必須です。 |
| Appで個人用として宣言された接続 | 実行する人の個人接続 | 実行する人がいない場合でも、共有接続へフォールバックしません。 |
| ProjectにOAuth／Bearer認証のMCPを登録 | 登録した人の認証情報（Project共有） | 登録時のアカウントがProject全員の共有認証情報になり、全メンバーの実行で使われます。最小権限の専用アカウントで登録します。 |
| Workflowトリガー | その開始ノードを最初に公開した人 | 別の人が再公開しても実行主体は変わりません。 |
| タスクスケジューラのタスク | タスクの作成者 | 編集しても実行主体は変わりません。 |
| トリガー・タスク共通 | — | 所有者が組織を離れると、自動的に無効化されます。 |

## この記事の範囲

この記事は、ロール・APIキー・外部接続・自動実行・Pageセッションに関する拒否または認証失敗を分けるための案内です。キーの発行・切替・失効は[Project APIキーを管理する](../operations/manage-project-api-keys.md)、外部接続の修復と引き継ぎは[接続の失効・担当者変更に対応する](../operations/handle-expired-connections-and-owner-changes.md)、Pageのアクセスモードの設定は[画面からPageを登録・公開する](../build/register-and-publish-pages.md)で扱います。Page自体のビルド・表示失敗、通信障害、入力内容のエラーを、本記事だけで認証・権限の問題と断定しません。

## まず確認すること

- [ ] 失敗した対象（画面操作、外部連携、自動実行、Page、API／SDK）と組織・Project・App名を特定しました。
- [ ] 操作した利用者、利用アカウント、APIキーの用途名、または接続名を区別して記録しました。
- [ ] HTTPステータス、表示メッセージ、応答本文の`requestId`、発生日時、再現手順を控えました。
- [ ] APIキー、パスワード、トークン、Cookie、Secretの実値をログ・画面共有・問い合わせに含めていません。
- [ ] 接続・キーを削除、再発行、再認証する前に、影響する自動処理や利用者を確認しました。

> エラーを解消するために、他者の認証情報を受け取る、キーをブラウザ側コードへ入れる、全スコープのキーを作る、全員へ共有する、といった対応は行わないでください。必要な対象・操作・担当を絞って確認します。

## 症状別に切り分ける

| 症状・表示されるメッセージ | 主な原因 | 確認・対処 | 詳しい記事 |
|---|---|---|---|
| 「この操作を行う権限がありません」「アクセスが拒否されました」「このエージェントを使用する権限がありません。管理者にお問い合わせください。」 | 組織ロール、Projectロール、IAM、個別リソースの共有・ポリシーのいずれかが不足 | 対象の組織・Project・リソースと、閲覧／実行／編集など失敗した操作を分けます。管理者は基本ロール、Project参加、必要ならIAMと共有範囲を確認します。利用者は自己判断でロールを変更せず依頼します。 | [組織・Project・Appの権限を理解する](../operations/understand-org-project-app-permissions.md) |
| 画面は開くが編集・削除・設定変更だけができない | 変更操作に必要なロールまたはIAM権限が不足 | どのボタン・対象で失敗したかを記録します。Projectの既定ロールに読み取り専用のものはないため、変更できない場合はカスタムロールやIAMで制限されていないかを確認します。最小限の必要な操作を管理担当者へ依頼します。 | [組織・Project・Appの権限を理解する](../operations/understand-org-project-app-permissions.md) |
| Projectのメンバーを追加・変更できない | 編集者・メンバーのロールではメンバーを管理できない | Projectの管理者に依頼します。編集者に変更しても解決しません。 | [組織・Project・Appの権限を理解する](../operations/understand-org-project-app-permissions.md) |
| API／SDKが401（Unauthorized）を返す、または「認証が必要です」 | 認証情報がまったく送られていない（401を返すのは一部の経路のみ） | キーが要求に付いているかを確認します。CLIでは接続先・キーの優先順位が「フラグ ＞ 環境変数 ＞ プロファイル」で固定されているため、意図しない設定が使われていないかも確認します。キー値を貼り直して共有しません。 | [Project APIキーを管理する](../operations/manage-project-api-keys.md) |
| API／SDKが403で「Invalid API key」を返す | キー値の誤り、削除・失効済みのキー、またはキーの作成者がProjectの有効メンバーでなくなった | 対象Project、キーの名前、削除・失効の有無、作成者のProject参加状況を確認します。作成者を外した場合は、その人が作ったキーがすべて無効になっています。実値は作成時にしか表示されないため、新しいキーを発行して安全に切り替えます。 | [Project APIキーを管理する](../operations/manage-project-api-keys.md) |
| API／SDKが403で「API key has expired」を返す | キーの有効期限切れ | 必要な最小スコープ・新しい期限で新規キーを発行し、切替後に旧キーを失効させます。 | [Project APIキーを管理する](../operations/manage-project-api-keys.md) |
| API／SDKが上記以外の403（Forbidden）を返す | 必要なスコープがない、または対象への実行権限がない | 要求した対象・操作と、キーに設定したスコープを照合します。スコープは作成後に変更できないため、不足している場合だけ最小スコープで新規キーを発行し、切替後に旧キーを失効させます。 | [Project APIキーを管理する](../operations/manage-project-api-keys.md) |
| 「要再認証」「連携が無効になっています。同じアカウントで再認証してください。」または「認証に失敗しました。問題が解決しない場合は管理者にお問い合わせください。」 | 外部サービスの認証期限切れ・解除・アカウント変更、または外部サービス側の権限変更。App導入・更新で追加または変更されたコネクタが未設定の場合もある | 個人接続か共有接続か、接続先、接続名、認証したアカウントを確認します。個人接続は本人が同じアカウントで再認証します。共有接続は利用者が別の個人接続で置き換えず、管理者が影響範囲を確認して対応します。Workflowは共有接続しか使わないため、個人接続を再認証してもWorkflowの失敗は直りません。 | [接続の失効・担当者変更に対応する](../operations/handle-expired-connections-and-owner-changes.md) |
| MCPツールが、実行した人ではなく別のアカウントの権限で動く | ProjectでOAuth／Bearer認証のMCPを登録すると、登録者の認証情報がProject全員の共有認証情報になる | 想定どおりの動作です。個人のアカウントで登録されている場合は、最小権限の専用アカウントで登録し直します。 | [外部ツール・データ連携・MCPを管理する](../operations/manage-external-tools-integrations-mcp.md) |
| 担当者の異動・退職後にトリガーや定期実行が動かない、権限エラーになる | トリガーは開始ノードを最初に公開した人、タスクは作成者として実行される。所有者が組織を離れると自動的に無効化される | 後任者が再公開・編集しても実行主体は変わりません。トリガーノードを削除して追加し直す（Webhook URL・Email by JAIのアドレスは変わります）か、タスクを作り直します。 | [定期実行を変更・停止・引き継ぐ](../operations/change-stop-handover-scheduled-runs.md) |
| Pageで操作中に認証を求められる、再読み込み後に利用できる／できない | Pageのアクセスモードに応じたサインインまたはPageセッションが失効・無効になった | まずPageのURL、アクセスモード、利用アカウント、直前の操作を確認します。再読み込みまたは案内された認証を一度行い、同じ症状が続く場合は繰り返さず、Page管理者へ連絡します。外部顧客認証のPageでは案内された認証経路を使います。 | [画面からPageを登録・公開する](../build/register-and-publish-pages.md)、[組織・Project・Appの権限を理解する](../operations/understand-org-project-app-permissions.md) |

## 401と403を読み分ける

| 状態 | 意味 | 最初に確認すること |
|---|---|---|
| 401（Unauthorized） | 認証情報がまったく付いていない。401を返すのは一部の経路のみ | キーが要求に付いているか、設定先（フラグ・環境変数・プロファイル）を確認します。 |
| 403「Invalid API key」 | キーが無効（値の誤り、削除・失効、作成者がProjectの有効メンバーでない） | キーの状態と作成者のProject参加状況を確認します。 |
| 403「API key has expired」 | キーの有効期限切れ | 新しいキーを発行して切り替えます。 |
| 上記以外の403 | 必要なスコープ、ロール、IAM権限の不足 | 要求した操作に必要なスコープ・権限を確認します。 |

無効なキーや期限切れのキーは401ではなく403になります。**401ならキーを作り直す、403なら権限を最大化する、と機械的に判断しないでください。** 応答本文のメッセージで原因を分けます。Studio APIのエラー応答には`requestId`が含まれます。CLIは既定の出力でこれを除去するため、問い合わせにはAPI／SDKの応答本文から控えます。

## 原因を分ける手順

1. **人のロールかを確認します。** ブラウザで特定の編集・管理操作だけが失敗する場合は、組織ロール、Projectロール、IAM、共有範囲を確認します。Projectへの参加と、個別リソースの操作権限は別です。
2. **APIキーかを確認します。** API／SDKで失敗する場合は、応答本文のメッセージ、対象Project、キーの用途名、期限、削除・失効、作成者のProject参加状況、必要スコープ、設定先を確認します。スコープは作成後に変更できないため、変更が必要なら新規発行・切替・旧キー失効を行います。
3. **外部接続かを確認します。** 「要再認証」「未連携」などでは、どの接続が使われたかを要点の表で確認し、接続の所有者と外部サービス側のアカウント・権限を確認します。担当交代時、後任者は前任者の個人接続を引き継ぐのではなく、自分の接続または共有接続を準備します。
4. **自動実行の実行主体かを確認します。** トリガー・タスクだけが失敗する場合は、実行主体（最初の公開者・タスク作成者・キー作成者）が組織やProjectに残っているかを確認します。
5. **Pageセッションかを確認します。** Pageの表示・操作中だけに発生する場合は、アクセスモードに合うアカウントまたは外部認証を確認し、再読み込み・再認証後の状態を記録します。Pageを公開設定に変更して回避しません。
6. **再現範囲を確認します。** 同じ利用者だけか、同じProjectの全員か、同じ外部サービス・APIキー・Pageだけかを分けます。重複した再実行や複数のキー発行は避けます。

## よくある誤解

- **「閲覧者」ロールを付ければ読み取り専用になる**：Projectに閲覧者のロールはありません。既定のメンバーでもAgentやWorkflowを実行でき、多くのリソースを作成できます。読み取り専用にするにはカスタムロールが必要です。
- **APIキーがあればすべてのAPIを呼べる**：対象Project、スコープ、有効期限、作成者のProject参加状況が関係します。
- **401ならキーの問題、403なら権限の問題**：無効・期限切れのキーも403です。応答本文のメッセージで分けます。
- **個人接続を再認証すればWorkflowも直る**：Workflowは共有接続しか使いません。
- **後任者が再公開すれば、自動実行は後任者の権限で動く**：トリガーは最初に公開した人、タスクは作成者として実行され続けます。
- **「接続済み」なら外部処理は成功する**：外部サービス側のデータ権限、認証アカウント、接続先の状態も確認します。
- **Pageで再認証されたら、権限を上げるべきである**：アクセスモードとPageセッションの問題か、実行する機能の権限かを分けます。

## 管理者・サポートに相談する前に

次を記録します。詳しい収集方法は、[問い合わせに必要な情報を集める](collect-info-for-support.md)を参照してください。

- 組織、Project、App／Page／APIの対象名、利用者またはキーの用途名（実値は除く）
- 失敗した操作・要求先、HTTPステータス、表示メッセージ、`requestId`、発生日時、再現手順
- 利用者のロール確認結果、必要な操作、個人／共有接続の別、再認証の実施有無
- APIキーでは期限・スコープ・削除／失効・作成者の参加状況・切替状況、自動実行では実行主体、PageではURL・アクセスモード・再認証後の状態
