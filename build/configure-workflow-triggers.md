# Workflowトリガーを設定する

**トリガー**を設定すると、メールの受信やデータの追加・更新などの出来事（イベント）をきっかけに、公開済みのWorkflowを自動で起動できます。この記事では、トリガーの追加、種類別の主な設定、テストと公開後の確認を説明します。

- 自動実行方式の選び方：[自動実行方式を選ぶ](../getting-started/choose-execution-method.md)
- 公開の手順：[Workflowを公開する](publish-workflow.md)

## トリガーとは

Workflowの起動方法には、主に次の3つがあります。

| 起動方法 | きっかけ | 設定する記事 |
|---|---|---|
| 手動 | 利用者が画面から実行する | [公開済みWorkflowを実行する](../use/run-published-workflow.md) |
| トリガー | メール受信・データ変更などのイベント | 本記事 |
| スケジュール | 決めた日時・間隔 | [タスクスケジューラを設定する](configure-task-scheduler.md) |

トリガーは、Workflowの**開始ノード**として追加します。1つのWorkflowに、手動の開始ノードとトリガーの開始ノードを併用できる場合があります。

> **トリガーは公開すると有効になります。** 下書きの状態ではイベントが起きても起動しません。設定画面には「トリガーを有効にするにはワークフローを公開してください」と表示されます。

## 始める前に

- 対象のWorkflowを編集・公開できる権限があることを確認します。
- 起動のきっかけにするイベント（どのメール、どのデータの、どの変化か）を具体的に決めます。
- 外部サービス（Gmail・Outlookなど）を使う場合は、連携に使うアカウントを決めます。
- 起動後の処理に外部への送信・更新が含まれる場合は、意図しない大量実行を防ぐため、絞り込み条件を決めておきます。

## 1. トリガーの開始ノードを追加する

1. 対象のWorkflowを編集画面で開きます。
2. 画面下部の操作パネルにある「ノードを追加」（＋のアイコン）を選択します。
3. 表示されたメニューの「トリガー」タブから、使う種類を選択します。
4. 開始ノードがキャンバスに追加されます。続けて、後ろに処理ノードを接続します。ノードの接続方法は[Workflowのノードを構成する](configure-workflow-nodes.md)を参照してください。

> **「ノードを追加」が表示されない場合**：トリガーの追加は組織の機能設定によって利用できないことがあります。組織の管理者に確認してください。

> **トリガーの種類は作成後に変更できません。** 別の種類にしたい場合は、新しい開始ノードを追加し、不要な開始ノードを削除してください。

### 選択できるトリガーの種類

表示される種類は、組織の機能設定やWorkflowの場所によって異なります。

| 画面上の名前 | 起動のきっかけ | 補足 |
|---|---|---|
| 手動トリガー | 利用者が画面から実行する | 入力フィールドを設定できる |
| Webhookトリガー | 外部システムからのHTTPリクエスト | 機能設定により表示 |
| カスタムオブジェクトトリガー | Objectのレコード作成・更新・削除 | Project内のWorkflowのみ。機能設定により表示 |
| ストレージトリガー | Storageのファイル・フォルダの変化 | Project内のWorkflowのみ。機能設定により表示 |
| データセットトリガー | Datasetのアイテム追加・更新・削除 | Project内のWorkflowのみ。機能設定により表示 |
| Gmail: 新着メール | Gmailでのメール受信 | Googleアカウントの連携が必要 |
| Outlook: 新着メール | Outlookでのメール受信 | Microsoftアカウントの連携が必要 |
| Email by JAI: 新着メール | 割り当てられた受信アドレスへのメール転送 | メールクライアント側で転送設定が必要 |
| Speech: 文字起こしの完了 | 会議の文字起こし完了 | 機能設定により表示 |

## 2. 種類ごとの設定をする

開始ノードを選択すると、右側に設定欄が表示されます。種類ごとの主な設定は次のとおりです。

| 種類 | 主な設定 | 公開後に決まるもの |
|---|---|---|
| 手動 | 入力フィールド | — |
| Webhook | HTTPメソッド、コンテンツタイプ、受け取るパラメータ（クエリ・ヘッダー・ボディ）、署名検証、カスタムレスポンス、必要に応じてチャレンジAPI設定 | Webhook URL |
| カスタムオブジェクト | 対象のオブジェクト、トリガータイプ（新規作成・更新・削除と、条件付きの各タイプ）、条件ビルダー、変更を検知するフィールド | — |
| ストレージ | 対象フォルダ、サブフォルダを含めるか、イベントタイプ、フィルター（ファイル名・拡張子・ファイルサイズ） | — |
| データセット | 対象データセット、トリガーアクション（アイテム追加・更新・削除）、データソース種別。Speechを選ぶ場合は文字起こし本文または要約 | — |
| Gmail／Outlook | アカウント連携、フィルター（件名・送信者・宛先・添付の有無など） | メール受信の開始 |
| Email by JAI | 転送元のメールアドレス | 受信アドレス |
| Speech | 会議フィルター（タイトル・会議タイプ・タグ・参加者） | 起動の対象となるアカウント |

### Webhookの署名検証と応答を設定する

Webhookでは、HTTPメソッドとコンテンツタイプを選び、クエリ・ヘッダー・ボディから取り出すパラメータを定義します。GETではボディの設定は表示されません。後続ノードで使う値は、開始ノードの「出力変数」で確認します。

送信元を検証する必要がある場合は、「署名検証」でGitHub、Slack、または「Custom」を選び、送信元と同じWebhookシークレットを設定します。GitHubとSlackを選ぶと署名ヘッダーが自動設定されます。シークレットや署名ヘッダーを、ノードの説明・プロンプト・実行履歴の共有資料に転記しないでください。

「カスタムレスポンス」では、レスポンスタイプ、ステータスコード、レスポンスボディを設定できます。レスポンスはWorkflowの処理より先に返されるため、ボディに挿入できるのはWebhookで受け取った変数です。必要に応じて、検証用リクエストに対してWorkflowを実行せずに応答する「チャレンジAPI設定」も設定します。GitHub・Slackの検証ハンドシェイクは自動処理されます。

### 条件で絞り込む

多くの種類で、起動する条件を絞り込めます。

- 条件を設定しない場合、対象のイベントすべてで起動することがあります。たとえばカスタムオブジェクトトリガーで「変更を検知するフィールド」を選ばないと、すべてのフィールドの変更で起動します。
- 条件の組み合わせ方（And／or、グループの扱い）は種類によって異なります。画面の説明を確認してください。
- 「含む」の条件は、想定外の値にも一致することがあります。代表的な例と、除外したい例の両方で確認してください。

### 外部アカウントを連携する（Gmail・Outlook）

1. 設定欄の「Google連携」または「Microsoft連携」で「連携」を選択し、アカウントを認証します。
2. 状態が「有効」になっていることを確認します。「要再認証」の場合は「再認証」を選択します。
3. Workflowを公開すると、メールの受信が始まります。状態表示が「メール受信中」になることを確認します。

> メールの内容は実行履歴に表示されます。機密性の高いメールが対象になる場合は、フィルターと実行履歴を閲覧できる範囲を確認してください。

### Email by JAIの受信アドレスを使う

- Email by JAIの開始ノードは、1つのWorkflowに1つだけ追加できます。
- 受信アドレスは公開後に割り当てられます。割り当てられたアドレスを、メールクライアントの転送先に設定します。
- 振り分け（どのメールを転送するか）は、メールクライアント側で設定します。
- 「アドレスを更新」を選ぶと、現在のアドレスは無効になります。転送ルールの再設定が必要です。

### Speechトリガーの対象アカウント

公開したユーザーの会議の文字起こし完了時に起動します。公開する担当者が変わると、対象の会議も変わる可能性があります。

## 3. 出力変数を後続ノードで使う

トリガーの開始ノードは、イベントの情報を**出力変数**として後続ノードへ渡します（例：メールの件名・本文、レコードのデータ、ファイルの情報）。

- 使える出力変数は、開始ノードの設定欄の「出力変数」で確認できます。
- 後続ノードで変数を参照する方法は[Workflowの変数・分岐を設定する](configure-workflow-variables-and-branches.md)を参照してください。
- 同じWorkflowに複数の開始ノードがある場合、どの開始ノードから起動したかによって、使える変数が異なります。分岐やテストで経路ごとに確認してください。

## 4. テストして公開する

1. 「一時保存」で下書きを保存します。
2. 編集画面のテスト実行で、トリガーの開始ノードを選んで実行します。
   - 種類によって、テスト用の値を入力する欄が表示されます（例：Gmail・Outlookはメールデータ、Webhookは設定したパラメータ）。
   - ストレージ・Email by JAIなど、入力欄がなく「入力パラメータは必要ありません」と表示される種類もあります。その場合は「実行を開始」で実行します。
3. 結果とステップを確認します。テストの方法は[Workflowの下書きをテストする](test-workflow-drafts.md)を参照してください。
4. [Workflowを公開する](publish-workflow.md)の手順で公開します。

> **テスト実行は、実際のイベントによる起動の確認ではありません。** テストでは入力した値（または空の値）で処理が動きます。外部サービスとの接続や絞り込み条件が正しく働くかは、公開後に確認してください。

## 5. 公開後に実際のイベントで確認する

1. 開始ノードの表示が、公開済み・受信中などの有効な状態になっていることを確認します。
2. 影響の少ないテスト用のイベントを起こします（例：テスト用の件名のメールを送る、テスト用のレコードを作成する）。
3. 実行ログで、起動したこと、および処理結果を確認します。確認方法は[Workflowの実行履歴でデバッグする](debug-workflow-run-history.md)を参照してください。
4. 起動しない場合は、次を確認します。
   - Workflowが公開済みか
   - 外部アカウントの連携が「有効」か
   - 絞り込み条件が厳しすぎないか
   - Webhook URLや受信アドレスが、連携元に正しく設定されているか

> イベントが起きてからWorkflowが起動するまでの時間や、すべてのイベントで必ず1回だけ起動することは保証されません。重複して起動しても問題が起きないよう、後続処理を設計してください。

## トリガーを止める・変更する

- トリガーの設定を変更した場合も、**公開するまで**稼働中のトリガーには反映されません。
- 下書きで開始ノードを削除しただけでは、公開版のトリガーは止まりません。停止・変更の正式な手順と影響は、[定期実行を変更・停止・引き継ぐ](../operations/change-stop-handover-scheduled-runs.md)で扱います。急ぎで止める必要がある場合は、Workflowの管理者に確認してください。
- 外部アカウントの連携が失効すると、トリガーが動かなくなることがあります。状態表示を定期的に確認してください。
