# Workflowの下書きをテストする

Workflowは、ノードが接続され、設定を保存できただけでは完成ではありません。この記事では、**編集画面から下書きを実行し、入力・処理経路・出力を確認して、修正と再テストを行う手順**を説明します。

ノードの構成は[Workflowのノードを構成する](configure-workflow-nodes.md)、変数・分岐の設定は[Workflowの変数・分岐を設定する](configure-workflow-variables-and-branches.md)を参照してください。ここでは下書きの検証までを扱い、公開は行いません。

## 始める前に

- 対象の組織・Project・Workflowと、編集・実行に必要な権限を確認します。
- ノード、モデル、指示、変数、分岐、終了ノードの出力を設定します。
- 外部サービスを使う場合は、接続先と使用するアカウントを確認します。
- 機密情報を含まないサンプル入力と、期待する結果を用意します。
- 稼働中のWorkflowを変更する場合は、関係者とテスト範囲を確認します。

本記事はパソコンのWorkflow編集画面と、手動開始のテストを中心に説明します。画面や入力項目は、開始ノードの種類・権限・提供状態によって異なります。

> **下書きのテストも実行です。** メール送信、データ更新、ファイル作成、外部API呼び出しなどを含む構成では、実際の接続先に影響する可能性があります。公開前であることを、模擬実行・無影響・無料の保証としないでください。まず外部更新のない構成、または許可されたテスト用の接続先で確認します。

## 1. テスト対象と合格条件を決める

### 編集画面から始める

対象ProjectでWorkflowの編集画面を開きます。公開済みWorkflowの一覧や利用画面からの実行と、編集中の下書きのテストは分けて扱ってください。

同じWorkflow名でも、公開済みの内容と編集中の内容が異なる場合があります。「どの入口から、どの変更を確認するか」を決めてから操作します。公開済みの内容を動かす手順は[公開済みWorkflowを実行する](../use/run-published-workflow.md)を参照してください。

### 成功表示だけを合格条件にしない

例えば「依頼文を要約し、至急の依頼は別の処理へ進める」Workflowなら、次を確認します。

| 観点 | 確認すること |
|---|---|
| 入力 | 入力した依頼文が、意図した変数に入っている |
| 参照 | LLMや条件分岐に、前段の正しい値が渡っている |
| 経路 | 意図した条件側、または「それ以外」側が処理されている |
| 出力 | 終了ノードで指定した項目に、期待する結果が返っている |
| 内容 | 要約に必要な情報が残り、原文にない事実を追加していない |
| 外部影響 | 送信・更新がある場合、対象と回数が意図どおりである |

この表は確認観点の例です。Studioが業務上の正しさを自動判定する機能ではありません。

## 2. 下書きを保存し、設定不備を確認する

1. ノードの設定を確認し、編集画面の「一時保存」を操作します。
2. 保存の成功を確認します。保存エラーが出た場合は、解消するまでテスト結果の比較に進みません。
3. 「チェックリスト」を開き、未接続のノード、必須項目、変数参照などの指摘を確認します。
4. 指摘されたノードを修正し、再度「一時保存」します。

編集画面からテストを開始する際にも、グラフを保存してから実行する処理があります。ただし、**実行前に明示的な一時保存を行い、何を検証するかを確定する**運用をおすすめします。

チェックリストで問題が見つからなくても、外部サービスの認証、実際の入力値、回答内容、分岐結果までは確認が終わっていません。また、Workflowが無効化されている場合は実行できないため、表示された案内と基本設定を確認してください。有効化が必要なときも、利用中の構成への影響を確認してから変更します。

> 入力フィールド設定内の「保存」、Workflowの「一時保存」、Workflowの「公開」は別操作です。下書きのテストを行うために、先に「公開」する必要はありません。

## 3. 開始ノードを選び、テスト入力を用意する

1. 編集画面の「実行」を選びます。
2. 「実行するスタートノードを選択」で、今回テストする開始ノードを選びます。
3. 開いた「Test Run」の「入力」タブを確認します。
4. 表示された項目にサンプル値を入力します。

開始ノードが複数ある場合は、名前だけでなく、手動入力などの種類と、確認したい経路が合っているかも確認してください。異なる開始ノードから実行した結果を、同一条件の比較として扱わないようにします。

### 手動入力の確認

- 必須項目を入力します。
- 初期値が入っている場合は、今回のテストで使いたい値か確認します。
- ファイル入力がある場合は、対象のファイルを指定し、アップロードの完了とエラーの有無を確認します。
- 入力項目がない構成では、入力不要の案内が表示されます。入力欄がないことだけで不具合とは判断しません。

対応形式、件数、容量は、入力項目の設定と画面の案内に従ってください。ここでは全Workflow共通の上限値を定めません。

手動のテスト入力で確認できる範囲と、メール受信など実際のイベントから開始する動作は同じではありません。イベント由来の開始条件は、[Workflowトリガーを設定する](configure-workflow-triggers.md)で別途確認します。

## 4. 「実行を開始」を選ぶ

入力と実行対象を確認したら、「実行を開始」を選びます。

入力不足などがあれば、表示された内容を修正します。ノード設定の不備がある場合は、ノード名や理由を含む案内が表示されることがあります。実行結果が作成されると「結果」タブへ移ります。

**結果画面へ移ったことと、全処理が成功したことは別です。** 「ステップ」で実行状態を確認し、出力がまだ表示されていない場合も、すぐに同じ処理を重ねて実行しないでください。

とくに外部送信・更新を含むWorkflowでは、通信エラーや表示待ちの間に再実行すると、処理が重複する可能性があります。実行履歴と接続先の状態を確認してから、再実行の可否を判断します。

## 5. 「結果」で最終出力を確認する

「結果」タブでは、Workflowが返した出力項目と値を確認します。ファイル出力がある場合は、ファイルとして表示される内容も確認します。

次の順に見ると、設定ミスと内容の問題を分けやすくなります。

1. **項目**：終了ノードで指定した出力項目があるか。
2. **値**：空欄、別ノードの結果、変数名だけの文字列になっていないか。
3. **形式**：期待した文章・構造化データ・ファイルになっているか。
4. **内容**：依頼に対して正しいか。不足や根拠のない追加がないか。

出力がない場合は、処理中、未設定、参照の誤り、実行失敗などを切り分けます。「結果」だけで原因が分からないときは、次の「ステップ」を確認してください。失敗時には、結果欄が一般的なエラー表示になる場合もあります。

## 6. 「ステップ」で値の流れと状態を確認する

「ステップ」タブには、実行の概要と、ノードごとの処理内容が表示されます。

### 実行の概要

状態、経過時間、クレジット、エラーなど、表示されている情報を確認します。クレジットが「計算中...」の場合は、ゼロと解釈しません。

| 状態の表示 | 次に確認すること |
|---|---|
| 実行中 | 完了状態と、確認できる処理結果を待つ。重複実行しない |
| 成功 | 出力の内容・形式・経路が合格条件を満たしているか |
| 失敗 | エラーとノードの入出力を確認し、問題箇所を切り分ける |
| 部分的成功 | 何が完了し、何が未完了かを確認する。全体成功と扱わない |
| 停止 | 実行済みの範囲や外部影響を確認する。未実行・巻き戻しと扱わない |

### ノードごとの確認

対象ノードを展開し、表示されている項目を確認します。

- **入力**：前段から渡された値や、今回指定した値。
- **プロセスデータ**：処理に関する情報。必要に応じて展開します。
- **出力**：そのノードが返した値。

すべてのノードに同じ情報が出るとは限りません。表示されている実行記録に基づき、最初に期待と異なった箇所を探します。

例えば、要約文が依頼内容と違う場合は、いきなり指示を書き直すのではなく、LLMに渡った入力が正しいかを先に確認します。条件分岐が意図と違う場合は、判定対象の値、比較方法、条件側の接続先を確認します。

> **「閉じる」は停止操作ではありません。** Test Runのパネルを閉じても、実行の取消や外部処理の巻き戻しが行われたとは扱わないでください。本記事では、このパネルに停止ボタンがあることを前提にした手順は案内しません。意図しない外部処理が疑われる場合は、追加実行を避け、実行履歴と接続先を確認して管理者へ連絡します。

## 7. 条件を変えて、経路ごとにテストする

1回の成功だけでなく、設定した経路ごとに確認します。以下は「依頼文に『至急』を含むか」で分岐する構成の例です。

| テスト入力の例 | 確認したいこと |
|---|---|
| 至急、見積もりの確認をお願いします | 「含む」の条件側へ進むか |
| 来週の打ち合わせ内容を整理してください | 「それ以外」側へ進むか |
| 至急ではありません | 否定文でも文字列「至急」を含むことを踏まえ、設定が業務目的に合っているか |
| 必須入力を空欄にする | 入力不足として実行前に案内されるか |
| 任意項目を空欄にする | 初期値や後段の処理が意図どおりか |

数値比較がある場合は、境界値の直前・一致・直後を用意します。追加条件や複数条件がある場合は、それぞれの経路、AND／ORの組み合わせ、条件が重複する入力も確認します。

分岐した経路を合流させる構成では、**実行されなかった側の出力を後段が必要としていないか**も確認してください。候補に変数が表示されることと、その実行で値が得られることは区別します。

この表はテスト設計の例です。自動実行されるテストセットではありません。

## 8. 修正して、同じ入力で再テストする

1. 期待との差を、入力・参照・条件・接続・指示・認証などに分けます。
2. 原因に関係する設定を修正します。
3. 「一時保存」の成功を確認します。
4. 編集画面の「実行」から、同じ開始ノードと同じ入力で再テストします。
5. 改善した点と、別の経路が崩れていないかを確認します。

原因を追いやすくするため、一度に多くの設定を変えず、変更内容を記録してください。同じ入力でもAIの文章が完全一致するとは限らないため、必要な情報、出力形式、禁止した内容などの基準で評価します。

再テスト前には、入力が保持されているかを毎回確認します。別画面の入力保持や履歴表示を、今回のテスト条件の保証として扱わないでください。

## 9. 実行履歴と検証メモを残す

編集画面の「実行履歴」から、対象の実行を選んで結果やステップを見直します。Workflow名、実行時点、Test Runの番号などを照合し、古い実行結果を修正後の結果と取り違えないようにします。

画面に「結果をダウンロード」が表示される場合は、実行情報をJSONファイルで保存できます。これは実行情報のダウンロードであり、Workflow定義のバックアップや公開操作ではありません。入力・出力を含む情報の持ち出しや共有は、組織のルールに従ってください。

次のひな形は、別のメモや管理表へ記録するための例です。Studioに専用の記録フォームがあることを示すものではありません。

| 記録項目 | 記入する内容 |
|---|---|
| 対象 | Project・Workflow・開始ノード |
| 変更内容 | 今回変更した設定 |
| テスト入力 | 機密情報を除いた入力内容、使用ファイルの識別情報 |
| 期待結果 | 経路、必要な情報、形式、外部影響 |
| 実際の結果 | 状態、出力、問題のあったノード |
| 実行の識別情報 | 日時、Test Run番号など確認できる情報 |
| 判定・残課題 | 合格／要修正と、その理由 |

実行履歴を使った詳細な調査は、[Workflowの実行履歴でデバッグする](debug-workflow-run-history.md)で扱います。

## 困ったとき

| 状況 | 確認すること |
|---|---|
| 実行できない | Workflowの有効状態、権限、開始ノード、入力不足、設定不備の案内 |
| 入力欄が想定と違う | 選択した開始ノード、保存済みの入力定義、手動／イベント由来の違い |
| 修正が反映されていないように見える | 編集画面から実行したか、一時保存が成功したか、表示中の実行が新しいか |
| 結果が空、または想定と違う | 実行状態、終了ノードの出力設定、前段の入力・出力、変数参照 |
| 分岐先が違う | 実際の比較値、文字列／数値、比較方法、AND／OR、接続先 |
| 外部連携で失敗する | 接続アカウント、権限、対象データ、接続先のエラー。再実行前に重複処理の有無を確認 |
