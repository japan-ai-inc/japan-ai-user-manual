# Storageのフォルダ構成を整える

Storageは、Projectで使う資料・入力ファイル・処理結果などを、フォルダ単位で配置できる場所です。構築物が扱うファイルの置き場を先に決めておくと、作成者・利用者が同じ保存先を選びやすくなり、AgentやWorkflowに渡す参照先、Storageトリガーの対象フォルダも確認しやすくなります。

この記事では、構築前に決めるフォルダ構成、Storage画面でフォルダを作成・整理する手順、構築物から利用するときの確認方法を説明します。ファイルのアップロードや取得は、[Storageのファイルを利用する](../use/use-storage-files.md)を参照してください。

- Storageトリガーの設定：[Workflowトリガーを設定する](configure-workflow-triggers.md)
- ファイルのアップロード・参照：[Storageのファイルを利用する](../use/use-storage-files.md)
- ファイル形式・容量などの条件：[Storageの仕様・制限](storage-specs-and-limits.md)

## フォルダ構成を決める目的

フォルダは、構築物の入力・出力の場所を共有する目印になります。まず、次の3点を分けて考えます。

| 分ける観点 | 決めること | 例 |
|---|---|---|
| 用途 | 入力、参照用、出力、作業中などの役割 | `01_input`、`02_reference`、`03_output` |
| 業務の単位 | 部門、顧客、案件、業務名、年度など | `sales`、`customer-a`、`2026` |
| 管理の単位 | 誰が更新し、いつ見直すか | 案件終了後に整理する、月次で出力を確認する |

最初は、利用者が保存先を選べ、構築担当者が参照・監視場所を説明できる最小限の構成にします。用途が増えた場合は、既存の参照先への影響を確認して追加します。

## 始める前に

- 対象のProjectと、既存のStorageに保存されているファイル・フォルダを確認します。
- 何を入力として受け取り、何を成果物として保存し、誰が更新するかを決めます。
- Agent、Workflow、Pageなど、Storageを使う構築物と担当者を洗い出します。
- Storageトリガーを使う場合は、監視対象にしたいフォルダ、サブフォルダを含めるか、起動したいイベントを決めます。
- 作成・名前変更・移動・削除の操作ができる権限があることを確認します。操作の表示や利用可否は、権限や組織の設定によって異なります。

> **既に使われているフォルダを整理する前に、参照元を確認してください。** Storageの画面ではファイルやフォルダのパスをコピーでき、Workflowのストレージトリガーでは対象フォルダを選択できます。名前変更や移動後に、既存の参照・設定が自動的に更新されるかは、この画面だけでは確認できません。変更前に、参照しているAgent・Workflow・Page・利用手順を確認し、変更後に実際の利用方法でテストしてください。

## 1. 構成案を作る

最初に、構築物と利用者の動きに合わせて、フォルダの役割を表にします。例えば、申請書を受け取り、Agentが内容を確認して結果を保存する場合は、次のように分けられます。

| フォルダ例 | 入れるもの | 主な利用者・構築物 | 運用上の注意 |
|---|---|---|---|
| `01_input` | 利用者が追加する申請書・CSV・添付資料 | 利用者、入力を読むAgent、起動元のWorkflow | 未処理と処理済みを混在させない運用を決めます |
| `02_reference` | 判断基準、テンプレート、参照資料 | Agent、作成担当者 | 更新担当者と版の扱いを決めます |
| `03_output` | 生成した報告書、確認結果、エクスポート | 利用者、後続の業務 | 出力名に日付や対象を含めるなど、探し方を決めます |
| `99_archive` | 利用を終えた資料 | 管理担当者 | 移動する時期と、参照が残っていないことの確認方法を決めます |

### 命名のルールを決める

フォルダ名は、画面で見た人が用途を判断できる名称にします。チームで表記をそろえると、保存先や参照先を伝えやすくなります。

| 観点 | 例 | 考え方 |
|---|---|---|
| 並び順 | `01_input`、`02_reference`、`03_output` | 用途の順に見せたい場合だけ連番を使います |
| 対象の識別 | `customer-a`、`2026-q1` | 顧客・案件・期間を、チームで分かる表記にそろえます |
| 状態の識別 | `working`、`approved`、`archive` | 作業中と確定済みを混在させないようにします |
| 名前の安定性 | `input`、`output` | 構築物が使う場所は、短期の業務名や担当者名だけで頻繁に変えないようにします |

フォルダ名から内容を推測できる場合があるため、機密情報を含めないよう確認します。

> 日付・版・担当者をすべてフォルダ階層にすると、保存先が深くなります。日付をファイル名に含めるなど、日常的にたどれる深さに抑えてください。

## 2. フォルダを作成する

1. 対象のProjectで「ストレージ」を開きます。
2. 新しいフォルダを作る場所へ移動します。画面上部の階層表示で、現在の場所を確認します。
3. 「フォルダ作成」を選択します。
4. 「新しいフォルダを作成」で「フォルダ名」を入力します。
5. 「作成」を選択します。
6. 一覧に作成したフォルダが表示され、「フォルダを作成しました」と表示されることを確認します。
7. 必要に応じてフォルダを開き、同じ手順で下位フォルダを作成します。

作成場所を間違えた場合は、現在の階層表示と構成案を見直します。作成できない場合は、権限や画面に表示される理由を確認します。

## 3. ファイルの保存先と構築物の参照先をそろえる

構成を作った後は、ファイルを置く人と構築物を設定する人が、同じフォルダを指していることを確認します。

### 入力・出力を分ける

1. 利用者がファイルを追加するフォルダを決めます。必要に応じて、説明や運用ルールを利用者へ共有します。
2. 処理結果を保存するフォルダを、入力フォルダとは別に決めます。
3. 同じファイルを更新して使うのか、結果を別ファイルとして残すのかを決めます。
4. テスト用ファイルを使い、意図したフォルダに保存・取得できることを確認します。

入力と出力を同じ場所に置くと、利用者が成果物を再度入力として選ぶ、または処理対象を探しにくくなることがあります。特にファイル追加をきっかけに処理する設計では、入力用フォルダを明確にし、出力先や保管先を分けることを検討してください。

### Agentでファイル・フォルダを参照する

Storageの一覧では、対象のファイルまたはフォルダに対して「パスをコピー（エージェントで使用可能）」を選択できます。コピーしたパスは、Projectの会話で参照先を指定する用途に使えます。

- パスは手入力で組み立てず、画面からコピーした値を使います。
- Agentに依頼するときは、対象、行ってほしい処理、変更や外部送信をしてよいかを明記します。
- フォルダを指定した場合に、配下のすべてのファイルが常に同じように扱われるとは限りません。回答や実行結果で、意図したファイルを参照したことを確認します。

Agentによる参照方法と、Storageに保存したファイルの扱いは[Storageのファイルを利用する](../use/use-storage-files.md)を参照してください。

### Workflowのストレージトリガーでフォルダを監視する

ストレージトリガーを設定する場合、Workflowの開始ノードで「対象フォルダ」を選択できます。「サブフォルダも含める」を選ぶか、対象にするイベントタイプ（フォルダの新規作成、ファイルの新規アップロード・更新・削除）を、構成案に合わせて設定します。

たとえば、`01_input`だけを監視対象にすれば、`03_output`に成果物を保存したことを入力として扱わない設計を検討できます。サブフォルダを入力単位として使う場合は、「サブフォルダも含める」の設定と、どの階層まで対象にするかを合わせて確認します。設定方法、公開、実際のイベントでの確認は[Workflowトリガーを設定する](configure-workflow-triggers.md)を参照してください。

> ストレージトリガーの表示・利用可否は、機能設定などの条件によって異なることがあります。また、構成変更後は、対象フォルダ、サブフォルダの扱い、イベントタイプが意図どおりかを公開前後に確認してください。

## 4. 名前変更・移動・削除を安全に行う

Storageでは、項目を選択して「名前を変更」、移動、削除を行えます。複数の項目を選択して移動・削除する操作もあります。整理の対象が構築物で利用されている場合は、次の順で進めます。

1. 対象のフォルダと配下のファイルを確認します。
2. Agent、Workflow、Page、利用手順などで、対象の名前・場所を使っていないかを確認します。
3. 影響を受ける利用者・担当者に、変更内容と実施日時を共有します。
4. 「名前を変更」または「移動」を実行します。同じ名前の項目がある場合は、置き換えや両方保持の選択肢を内容を確認して判断します。
5. 構築物の設定や利用手順を必要に応じて更新します。
6. 実際の利用方法で、ファイル参照・保存・トリガー起動などを確認します。

削除時には、フォルダを削除すると配下のファイルとフォルダもすべて削除され、元に戻せない旨が表示されます。不要と判断できるまで削除せず、残す必要があるファイル、参照中の構築物、移行先を確認してください。

組織ドライブでは、非管理者が他の利用者の完了済みファイルを削除しようとすると、画面上で削除がブロックされます。フォルダを含む削除可否は、対象ごとにサーバー側で権限確認されます。削除できない場合は、作成者または管理者に確認してください。同名項目との競合時の扱いは、画面に表示される選択肢を確認してから進めます。

アプリによって管理されているファイルは、読み取り専用として表示され、通常の変更操作ができない場合があります。利用のためにアプリの更新・削除や設定変更を行う前に、アプリの担当者へ確認してください。
