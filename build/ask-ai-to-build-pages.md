# AIにPageの作成・修正を依頼する

AIに業務画面の目的と条件を伝え、Pageの作成または既存Pageの修正を依頼します。Pageは、情報の確認、入力、業務上の操作を行うためのWeb画面です。本記事では、**要件を整理する → AIに依頼する → プレビューで確認する → 修正を依頼する → 登録・公開の状態を確認する**流れを説明します。

AIが「完了」と返答しただけでは、Pageが業務で使えるとは限りません。画面の見た目だけでなく、入力、表示されるデータ、実行する操作、アクセスできる利用者を実際に確認してください。Pageの登録・公開の詳しい手順は、[画面からPageを登録・公開する](register-and-publish-pages.md)で扱います。

## 始める前に

- 対象の組織・Projectと、作成するPageまたは修正するPageを確認します。
- AIとの会話を始められ、対象ProjectのPageを作成・更新できる権限があることを確認します。利用できる機能や権限は、組織・Projectの設定によって異なります。
- 新規作成では、最初に提供する業務を1つに絞ります。既存Pageの修正では、対象のPage名、直したい画面、変更しない機能を決めます。
- 確認に使う架空データまたは利用を許可された検証データを準備します。個人情報、顧客情報、パスワード、APIキーなどを会話に入力しないでください。
- 実際に外部送信、データ登録・更新・削除を行う画面では、検証時の影響範囲と確認担当者を決めます。

> Pageの作成・修正をAIに依頼することと、利用者向けに登録・公開することは別の作業です。新規作成時の計画承認や、会話内の「実行してよい」という指示が、利用者への公開確認を自動で代替するわけではありません。

## 1. 作りたい業務画面を整理する

最初に「見栄えのよい画面」ではなく、利用者が画面で完了させたい業務を言葉にします。要件が不足すると、画面は表示できても、必要なデータや操作がそろわないことがあります。

| 整理する項目 | 伝える内容 | 例 |
|---|---|---|
| 目的 | Pageで終わらせたい業務と、成功の判断 | 営業担当者が商談準備の漏れを確認する |
| 利用者 | 使う人、利用場面、利用頻度 | 営業担当者が商談前に利用する |
| データ | 表示・入力する項目、参照先、扱わない情報 | 会社名、商談日、担当者メモ。検証用データのみ |
| 画面 | 必要な一覧、詳細、入力欄、並び順、初期表示 | 上部に検索、中央に案件一覧、右側に詳細 |
| 操作 | 検索、絞り込み、登録、更新、AI実行などの結果 | 「確認済み」を記録し、完了メッセージを表示する |
| 権限 | 誰が閲覧・操作できるか、外部利用の有無 | 営業担当者は閲覧・更新、管理者だけが設定変更 |
| 完成条件 | 何を試して、どの結果なら完了か | 3件の検証案件を絞り込み、入力内容が正しく反映される |

「顧客管理画面を作って」のような広い依頼ではなく、今回の対象と対象外を明確にします。たとえば、最初は検索と表示だけにし、登録・更新や外部サービスへの送信は次の段階に分けると、確認する範囲を小さくできます。

### 依頼前に決めること

既存Pageを修正する場合は、まず現在の画面を開き、変更する箇所を特定します。画面上でプレビュー表示を利用できる場合は、修正したい部分を指し示してから依頼します。選択した位置はAIにとって画面上の手掛かりであり、正確な変更対象を保証するものではありません。似た項目がある、または何を変えるか曖昧なときは、画面の名称・現在の文言・期待する文言も文章で伝えてください。

また、既存の入力・保存・外部連携を含むPageでは、変更によって何が起こるかを先に確認します。見た目だけを直す依頼でも、関連する表示条件や操作を意図せず変えないよう、「今回変更しないもの」を明記します。

## 2. AIに作成・修正を依頼する

対象Projectで構築用のAIとの会話を開きます。構築用のAIを選ぶ方法、計画を確認して実行する方法、実行結果の一般的な確認は、[Studio Assistantに構築を依頼する](build-with-studio-assistant.md)を参照してください。

依頼では、最初に新規作成か既存Pageの修正かを示し、続けて前節の要件を伝えます。いきなり実装を求めるのではなく、既存Pageを修正する場合は対象を確認し、作成・変更する内容とテスト方法を先に整理するよう依頼します。

### 新規Pageの依頼例

> このProjectに、営業担当者が商談準備を確認するPageを作成したいです。利用者は営業担当者で、商談前に会社名、商談日、担当者メモを確認します。
>
> 画面の上部に会社名で絞り込める検索欄、中央に検証用の案件一覧、選択した案件の詳細を表示してください。最初は表示と検索だけを対象にし、データの登録・更新、外部サービスへの送信、既存Pageの変更は行わないでください。
>
> まず、作成する画面、使う検証データ、変更対象、確認手順を提案してください。実行後は、作成したPageの名前、確認した操作、未確認の項目を分けて報告してください。

### 既存Pageの修正例

> 「商談準備」Pageの案件一覧を修正してください。会社名の検索欄の下に、商談日で絞り込む項目を追加し、一覧には会社名、商談日、担当者名を表示してください。
>
> 登録・更新の処理、アクセス設定、他のPageは変更しないでください。変更前後で、会社名検索と商談日の絞り込みを検証用データで確認し、結果を報告してください。対象が判断できない場合は、変更せずに質問してください。

> 「作成して」「修正して」だけでは、AIが想定する完成範囲と一致しない場合があります。依頼文には、データの出所、実行してよい操作、変更しない範囲を含めてください。AIへの文章上の指示は、アクセス権や外部連携に対する技術的な制御の代わりにはなりません。

## 3. 実行前に変更範囲を確認する

AIから計画や確認事項が返ったら、次を確認してから実行を依頼します。

- 対象ProjectとPage名が正しいか。新規作成か既存Pageの修正かが明確か。
- 利用者、目的、表示するデータ、入力項目が要件に合っているか。
- 画面に用意する操作と、その操作で登録・更新・送信される対象が分かるか。
- 既存Page、既存データ、アクセス設定、外部連携のうち、触れない対象が除外されているか。
- 確認に使うデータと、正常時・情報が不足する時の確認方法が決まっているか。
- 登録、公開、アクセス設定、バージョン切り替えを今回行うのか、後続作業に分けるのかが明確か。

計画に不要な操作が含まれている場合は、範囲を絞って書き直してもらいます。作成直後のProjectで計画を承認する場合は、「承認」が実行開始の操作であることを理解したうえで進めます。通常の会話では、同じ承認画面が必ず表示されるわけではないため、実行してよい対象を文章で明示します。

AIへのPage構築依頼でProject設定やリソースに変更を加える場合は、Project名・説明、変更対象、実行を妨げる条件、進行状況を確認します。失敗した工程に「再試行」または「スキップ」が表示されても、理由を確認せずに続けないでください。権限不足や接続先からの拒否などが表示された場合は、対象・権限・実行してよい範囲を見直します。

## 4. プレビューと業務操作を確認する

AIの作業後は、対象Pageを開いて確認します。画面のカードや一覧から開く方法は[Pageから業務を進める](../use/work-with-pages.md)を参照してください。画面を開けたことだけで完了とせず、要件ごとに確認します。

1. 対象のPage名と、AIが報告した作成・変更内容を照合します。
2. プレビュー表示を利用できる場合は、目的の画面が表示されるか確認します。読み込みエラーや白い画面がある場合は、完了として扱いません。
3. 一覧、見出し、入力欄、ボタン、説明文が、依頼した業務と利用者に合っているか確認します。
4. 検証用データで、検索・絞り込み・表示・入力・確定など、今回依頼した操作を1つずつ試します。
5. データを登録・更新・送信する操作がある場合は、画面の表示だけでなく、対象の保存先または送信先で結果を確認します。
6. 必須情報がない場合、検索結果がない場合、権限がない場合など、想定外の状態での表示も確認します。

| 確認する観点 | 確認内容 |
|---|---|
| 目的・導線 | 利用者が最初に行う操作と、次に取る行動が分かるか |
| データ | 対象の情報だけを表示し、検証データと本番データを混同していないか |
| 入力 | 必須項目、形式、入力エラーの案内が業務上理解できるか |
| 操作結果 | 実行、保存、更新、送信の結果を確認でき、同じ操作を重ねて実行しないか |
| 権限・公開範囲 | 利用者に必要な操作だけが許可され、意図しない人へ開放されていないか |
| 画面表示 | PCの利用場面で、文字、表、ボタンが読め、重要な情報が隠れていないか |

> Page内の「登録」「送信」「実行」などは、実際のデータや外部サービスに影響することがあります。表示の動作確認と業務処理の実行を区別し、処理済みか不明なときは確認せずに再実行しないでください。

## 5. 差分を絞って修正を依頼する

期待と異なる箇所があれば、Page全体を作り直すよう頼む前に、差分を具体的に伝えます。対象、現在の状態、期待する状態、変更しないもの、再確認する操作をセットで示すと、影響範囲を抑えやすくなります。

> 「商談準備」Pageを修正してください。現在は案件一覧が会社名だけを表示しています。会社名の右に商談日と担当者名を表示し、商談日が未入力の場合は空欄ではなく「未設定」と表示してください。検索、アクセス設定、登録・更新の処理は変更しないでください。変更後に、商談日がある案件とない案件をそれぞれ確認してください。

修正後は、前回の結果ではなく、更新後のPageをもう一度プレビュー表示で確認します。既存Pageを更新した場合は、以前の状態に戻す必要がある場面に備え、現在適用されている内容と変更の目的を記録します。Pageには「バージョン履歴」と「復元して適用」の操作が表示される場合がありますが、切り替え前に利用者への影響を確認してください。バージョンの扱いは[Pageのバージョンを管理する](manage-page-versions.md)で説明します。

## 6. 登録・公開とアクセス設定を確認する

作成・修正の確認後、Pageを誰がどの入口から利用するかを確認します。Page一覧に見えること、Pageを開けること、外部の利用者に提供できることは同じ状態ではありません。

- Pageが対象Projectに登録され、必要なPageを開けるか確認します。
- 「新しいバージョンをアップロード」や更新が行われた場合は、意図した内容が現在適用されているか確認します。
- 「アクセス設定」が表示される場合は、サインインの要否と利用者の範囲を確認します。設定できる選択肢は組織の機能設定により異なる場合があります。
- 外部の利用者に案内する前に、登録・公開・URL共有の条件を管理担当者と確認します。

登録・公開の操作やアクセス設定を、画面作成の完了報告だけで済ませないでください。利用者が実際に使う入口と権限で、業務操作まで確認してから提供します。
