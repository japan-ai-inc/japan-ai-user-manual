# 自動実行方式を選ぶ

Studioで処理を動かすときは、**「何を実行するか」と「何をきっかけに始めるか」を分けて考えます。**

例えば、週次レポートを作るWorkflowがあっても、それだけで毎週動くわけではありません。人が実行するのか、日時を決めて実行するのか、データの変更に合わせて実行するのかを選びます。

この記事では、自動化を始める前の比較対象として手動実行も含め、Workflowトリガーと「タスク」で管理する日時起動の使い分けを説明します。具体的な設定操作や対応イベントの一覧は、各設定記事で扱います。

## 最初に分ける2つのこと

| 決めること | 例 |
|---|---|
| **実行する処理** | Agentによる報告文の作成、Workflowによる情報取得・集計・登録 |
| **開始するきっかけ** | 担当者が実行する、毎週決まった日時になる、対象のメールを受信する |

AgentやWorkflowなどの機能選択から確認したい場合は、[目的から機能を選ぶ](choose-features-by-goal.md)を参照してください。

## 目的から実行方式を選ぶ

| 業務の条件 | 第一候補 | 選ぶ理由 |
|---|---|---|
| 入力内容や実行してよいかを、その都度人が判断する | **手動実行** | 担当者が入力や対象を確認してから開始できる |
| 指定した日時、または毎日・毎週などの周期で実行する | **「タスク」で管理する日時起動** | AgentまたはWorkflowの実行タスクを、日時に合わせて管理できる |
| メール受信やデータの変更など、出来事に応じて実行する | **Workflowのイベントトリガー** | 対象の出来事と条件を設定し、その情報を処理へ渡せる |
| 外部システムからの通知をきっかけに実行する | **Webhookトリガーを検討する** | 利用できる場合、外部から届くHTTPリクエストを起点にできる。接続・認証・入力形式の確認が必要 |

これは選択の目安です。利用できるトリガーや設定画面は、提供条件・組織の設定・権限・対象Workflowによって異なります。候補となる方式が、実際に利用する環境で使えることを確認してください。

> 「トリガー」は、処理を始めるきっかけを意味します。画面や技術資料では手動実行を含めて使われる場合もあります。この記事では、出来事を起点とするものを「イベントトリガー」、日時を起点とする設定を「スケジュール」と呼び分けます。

## 1. まず手動実行を選ぶ場合

次のような業務は、手動実行から始めます。

- その都度、対象の期間・ファイル・依頼内容を変える。
- 外部への送信やデータ更新の前に、人が実行の可否を判断する。
- 新しく作った処理の入力・結果・影響を確認する。

例えば、担当者が対象案件を選び、報告文の下書きを生成するケースです。最初は自動送信まで組み込まず、結果を確認できる構成で試します。

Workflowでは、作成者が行う下書きのテストと、利用者が行う公開済みWorkflowの実行を区別してください。**テスト実行でも、含まれる処理によっては実データの更新や外部への送信が発生します。** テストという名前だけで、安全な仮実行になるとは考えないでください。

また、手動で処理を開始することと、途中の各操作で人の承認を求めることは別です。必要な確認箇所は、処理の設計として用意します。

## 2. 日時が決まっているなら「タスク」

日時起動の実行タスクは、「タスク」ページで管理します。ここでは、実行するAgentまたはWorkflowと、日時や繰り返しの条件を確認・設定します。

例えば、次のような業務が候補です。

- 毎朝、前日分の情報を集計する。
- 毎週、対応状況の報告文を作る。
- 指定した日時に、準備済みの処理を実行する。

選ぶ前に、次の点を決めます。

| 確認すること | 判断の例 |
|---|---|
| 実行対象 | どのAgent・Workflowを動かすか |
| 入力・対象期間 | 毎回同じ入力でよいか。「前日」「前週」を処理の中でどう特定するか |
| 日時・周期 | 何時に、どの頻度で実行するか。画面のタイムゾーンと次回実行日時が意図どおりか |
| 終了・停止 | いつまで続けるか。不要になったとき誰が停止するか |
| 結果確認 | どこで履歴を見るか。通知が必要か、誰が失敗に対応するか |

スケジュールを設定しただけで、入力の期間が自動的に切り替わったり、必要なデータが揃ったりするわけではありません。例えば、毎朝の集計でも、元データの更新が遅れていれば未反映の情報が生じます。

**指定した時刻と、処理が完了する時刻は同じではありません。** 実行状況や外部サービスの応答も含め、結果を確認できる運用にします。

## 3. 出来事に合わせるならWorkflowトリガー

Workflowのイベントトリガーは、対象の出来事が発生し、設定した条件に合う場合に処理を開始するための設定です。

候補には、メールの受信、Objectのデータ変更、Storageのファイル操作などがあります。ただし、サービスやイベントの種類ごとに対応条件が異なります。「外部サービスのどんな変更でも検知できる」という意味ではありません。

### イベント方式で決める3点

1. **どこで起きた出来事か**：対象アカウント、Project、Object、フォルダなど。
2. **どの出来事を対象にするか**：受信、作成、更新など、利用できる種類と絞り込み条件。
3. **何を入力として渡すか**：対象レコード、メール本文、ファイル情報など、Workflowが必要とする値。

例えば、対象フォルダにファイルが追加されたら内容を整理したい場合は、「どのフォルダか」「追加イベントに対応しているか」「ファイルを処理に渡せるか」を確認します。保存場所だけを決めても、自動実行は設定されません。

### Webhookで外部からの通知を利用する場合

「Webhookトリガー」を利用できる場合は、外部システムからのHTTPリクエストを受けてWorkflowを起動できます。公開後に生成されるWebhook URLを外部システムへ設定し、受信先、署名検証を含む認証方法、送るデータの形式、Workflowの入力との対応を確認します。

外部側が通知を送らなければ、その通知をきっかけに実行することはできません。SDK・APIから直接実行する設計も別の選択肢ですが、対応範囲は開発者ガイドで確認してください。

### 処理の公開と接続の準備を分ける

Workflowの処理内容ができていても、接続先の認証、イベント条件、トリガー登録などの準備が残っている場合があります。

**「手動で動いた」「公開できた」だけで、自動実行も準備完了とは判断しません。** 実際の条件に合う出来事を使って、起動と結果まで確認します。

## 日時起動とイベント起動で迷う場合

「何に合わせて動かしたいか」で判断します。

| 目的 | 判断 |
|---|---|
| 毎朝、その時点のデータをまとめたい | 日時起動が候補。対象期間と集計時点を決める |
| 1件のデータが追加されるたびに処理したい | 対応するイベントトリガーが候補 |
| 元データの準備が終わってから処理したい | 準備完了を表すイベントが利用できるか確認。単に時刻を遅らせるだけでは準備完了を保証できない |
| 例外が多く、対象や実行可否を毎回判断したい | 手動実行を残すか、定型部分だけを自動化する |

「タスク」で管理する日時起動とWorkflowトリガーは、利用者が設定する目的・入口を区別するための分類です。内部で別々の実行基盤を使う、という意味ではありません。

同じ処理に日時起動とイベント起動を両方設定する場合は、同じ対象が二重に処理されないかを確認します。起動方式を増やせば確実になる、とは限りません。

## 自動化する前のチェックリスト

- [ ] 対象データと、処理の成功条件を決めた。
- [ ] テスト用の入力で、結果と更新・送信の影響を確認した。
- [ ] 誰の権限・アカウントでデータを参照し、外部サービスを操作するか確認した。
- [ ] 日時・タイムゾーン、またはイベントの対象・条件を確認した。
- [ ] 認証情報の失効や、担当者変更時の対応先を決めた。
- [ ] 実行履歴の確認場所と、失敗時の担当者を決めた。
- [ ] 再実行や重複起動で、同じデータの二重登録・二重送信が起きないか確認した。
- [ ] 停止・変更の方法を確認した。停止が実行中の処理にも及ぶかは、別途確認する。

画面に結果が出ない場合も、処理自体が続いている可能性があります。すぐに再実行せず、まず履歴と処理先の状態を確認してください。

最初は対象を限定して試し、通常のケースだけでなく、対象なし・入力不備・接続エラーのケースも確認してから利用を広げます。
