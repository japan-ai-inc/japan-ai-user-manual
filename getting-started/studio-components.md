# 構成機能の役割

Studioでは、AIによる処理、業務データ、利用者向けの画面を組み合わせて、業務に合った仕組みを作ります。

この記事では、Agent・Workflow・Skill・Page・Object・Dataset・Storageの役割と、機能同士の関係を説明します。作成手順ではなく、「何を担当する機能か」を理解するための記事です。

ProjectやAppとの関係を先に確認したい場合は、[「Studio Workspace・Project・App・Marketplaceの関係」](studio-concepts.md)を参照してください。

## まず押さえる7つの機能

| 機能 | 主な役割 | 業務での例 |
|---|---|---|
| **Agent** | 指示や依頼に応じて、AIが回答や処理を行う | 問い合わせへの回答、情報整理、文章の下書き |
| **Workflow** | あらかじめ組み立てた処理の流れを実行する | 情報取得→分類→条件分岐→データ登録 |
| **Skill** | Agentが再利用する手順・知識・関連資料などをまとめる | 報告書の作成ルール、調査の進め方 |
| **Page** | 利用者が情報を見たり操作したりするWeb画面を提供する | 入力フォーム、一覧画面、ダッシュボード |
| **Object** | 項目を定義し、業務データをレコードとして管理する | 問い合わせ番号、担当者、対応状態 |
| **Dataset** | AIが検索・参照する資料をまとめる | 社内規程、製品マニュアル、FAQ |
| **Storage** | ファイルやフォルダを保管・管理する | 添付PDF、画像、CSV、生成した報告書 |

これらは役割の違いを理解するための整理です。すべての機能を必ず使う必要はありません。表示される機能や利用できる操作は、提供条件・組織の設定・権限によって異なります。

## 処理を担う：Agent・Workflow・Skill

### Agent：依頼を受けて回答・処理する

Agentには、担当する業務や回答の方針などを設定します。利用者の依頼を受けて、文章を作成したり、参照情報を整理したりします。

必要な設定を行うことで、Datasetを検索したり、ツールを使ってデータや外部サービスを操作したりする構成にできます。Agentを作成しただけで、すべての資料やサービスを利用できるわけではありません。

例えば、問い合わせ内容と製品マニュアルをもとに、回答の下書きを作る役割を担当させます。

### Workflow：処理の流れを組み立てる

Workflowでは、処理の単位である「ノード」をつなぎ、入力から結果までの流れを設定します。

複数のAgentを連結するだけでなく、AIモデルによる処理、資料検索、条件分岐、繰り返し、データ操作などを組み合わせます。

例えば、「問い合わせを受け取る→分類する→分類に応じて処理を分ける→対応記録を登録する」という流れです。必要な部分だけでAgentを呼び出すこともできます。

> Workflowは処理の流れを定義する機能です。AIによる生成や外部サービスの応答を含む場合、毎回同じ結果になることまで保証するものではありません。

### Skill：Agentが使う進め方を再利用する

Skillには、業務を進めるための手順や注意点、参照資料などをまとめます。内容に応じて、ツールやスクリプトなどを組み合わせる場合もあります。

例えば「回答文には結論・理由・参照元を含める」「報告書ではこの項目を確認する」といった進め方を、再利用できる形にします。

**SkillはAgentそのものでも、Workflowのノードをつないだ処理定義でもありません。** Skillの利用だけで、外部サービスの認証やデータのアクセス権が付与されるわけでもありません。

### 3つの関係

- **Agent**は、依頼に応じて回答・処理を行います。
- **Workflow**は、どの処理をどの順序・条件で実行するかを定義します。
- **Skill**は、Agentが仕事を進めるための再利用可能な手順や知識を提供します。

それぞれを別々に使うことも、組み合わせることもできます。例えば、Workflowの一部で、Skillを利用するAgentに回答の下書きを依頼する構成が考えられます。実際に利用できる組み合わせには設定と動作確認が必要です。

## 情報を扱う：Object・Dataset・Storage

この3つは、いずれも情報を扱いますが、主な用途が異なります。

### Object：項目を持つデータを管理する

Objectでは、業務に必要な項目を定義し、1件ずつのデータをレコードとして管理します。

例えば「問い合わせ」というObjectに、問い合わせ番号・内容・担当者・対応状態を登録します。表形式のデータを検索したり、状態を更新したりする業務に利用します。

画面に表示する項目だけでなく、データの型や閲覧・更新できる範囲も設計します。

### Dataset：回答や処理の根拠となる資料を検索する

Datasetは、AIが必要な情報を検索・参照するための資料のまとまりです。例えば製品マニュアルやFAQを取り込み、Agentが問い合わせに関連する情報を探す構成にします。

資料の取り込みと、Agentなどから参照するための設定が必要です。また、資料を更新した際には、取り込み・同期の状態を確認します。

Datasetによる検索は、登録資料を毎回すべて読み切ることを意味しません。全文の比較や漏れのない抽出が必要な業務では、資料の読み取り方法も含めて別途設計します。

### Storage：ファイルを保管する

Storageは、PDFや画像、CSVなどをファイルとして保管する場所です。業務で受け取った添付ファイルや、処理によって生成された報告書などを整理できます。

保管したファイルをAgent・Workflow・Pageなどから利用する場合は、そのための読み取りや連携を設定します。

**Storageにファイルを置くことと、Datasetへ資料を取り込んで検索対象にすることは、同じ操作ではありません。** 保存しただけで、すべてのAgentの回答根拠に自動追加されるとは考えないでください。

### 同じ業務で使い分ける例

| 扱う情報 | 主に使う機能 | 管理の仕方 |
|---|---|---|
| 問い合わせの担当者・対応状態 | Object | 項目を持つレコードとして登録・更新する |
| 回答時に参照する製品マニュアル | Dataset | 関連する説明を検索できるように取り込む |
| 問い合わせに添付された画面画像 | Storage | ファイルとして保存し、必要な処理から参照する |

同じ元資料を複数の用途で扱う場合もあります。その場合は、保存先ごとの役割と更新方法を決めておきます。別の場所にあるデータが自動的に同じ状態になるとは限りません。

## 利用者の入口を作る：Page

Pageは、情報を表示したり、利用者が入力・操作したりするためのWeb画面です。例えば、問い合わせの登録フォーム、対応状況の一覧、集計結果のダッシュボードを用意できます。

必要な連携を実装することで、PageからObjectのデータを表示・更新したり、AgentやWorkflowによる処理を呼び出したりできます。

**PageはApp全体と同じ意味ではありません。** 画面を担う構成要素であり、表示するデータや呼び出す処理は別途組み合わせます。Pageを作らず、チャットなどを入口にする構成もあります。

画面操作やAIへの依頼で進められる作業もありますが、独自の画面や処理の開発には、Web開発の知識が必要になる場合があります。

## 組み合わせ例：問い合わせ対応を支援する

次の例は、各機能の役割を示す構成例です。標準で設定済みのアプリを表すものではありません。

1. **Page**に、問い合わせの入力画面と対応状況の一覧を用意します。
2. **Object**に、問い合わせ内容・担当者・状態を保存します。
3. 添付ファイルがある場合は、**Storage**に保存します。
4. **Dataset**に、回答の参考となる製品マニュアルやFAQを準備します。
5. **Agent**が関連資料を参照し、回答の下書きを作ります。**Skill**には、回答を作るときの手順や注意点をまとめます。
6. 定型化したい処理は、**Workflow**で組み立てます。
7. 担当者が、回答の根拠と内容を確認して業務に利用します。

最初からこの全構成が必要なわけではありません。まずAgentとDatasetで資料を参照する仕組みを作り、必要になった時点で管理用のデータや画面を加える進め方もできます。

## 機能をつなぐ前に確認すること

機能を配置するだけで、相互に利用できる状態になるわけではありません。次の点も設定・確認します。

- **参照・接続先**：どの資料、データ、ファイル、処理を利用するか。
- **権限**：誰が閲覧・実行・登録・更新できるか。
- **認証情報**：外部サービスを誰のアカウントで操作するか。
- **動作確認**：期待する結果が出るか、意図しない更新や送信が起きないか。

外部サービスの操作には対応するツールや接続設定が必要です。SDK・APIは、コードから機能を利用するための手段であり、これらの権限や認証を不要にするものではありません。
