# 目的から機能を選ぶ

Studioで何かを作りたいときは、最初に機能を全部そろえるのではなく、**「誰が、何を入力し、何を受け取れば仕事が進むか」**を決めます。その目的に必要な機能だけを組み合わせると、試しやすく、運用や変更もしやすくなります。

この記事は、作成者が最初の構成を決めるための判断ガイドです。各機能そのものの説明は、[構成機能の役割](studio-components.md)を参照してください。

## 1. 作る前に、使えるものがないか確認する

すでに目的に合うAppや、参加できるProjectがあれば、新規に作る必要がない場合があります。

- **導入済みのAppがある**：そのAppの利用案内と、自分が利用できる範囲を確認します。
- **共有されたProjectがある**：使えるAgent・Workflow・Pageなどを確認します。
- **Marketplaceに候補がある**：機能、導入条件、必要な接続、費用を確認し、導入を担当する人へ相談します。
- **既存のものでは目的を満たせない**：不足する部分を整理し、新規作成や既存構成の変更を検討します。

既存リソースの再利用では、リンクとコピーを混同しないようにします。元の設定を変更したときに他の利用者へ影響しないか、確認してから進めてください。

## 2. 目的を1文にする

次の形で書くと、必要な処理やデータを整理できます。

> ［利用する人］が、［入力する情報］を使って、［必要な結果］を得る。

例えば、次のように具体化します。

> 問い合わせ担当者が、顧客からの質問と製品マニュアルを使って、根拠を確認できる回答の下書きを得る。

この段階では「回答を自動送信する」まで広げず、まず下書きが役立つかを確かめる構成にできます。

合わせて、次の4点を決めます。

| 確認すること | 例 |
|---|---|
| 入力 | 質問文、対象期間、PDF、案件番号 |
| 出力 | 回答の下書き、集計表、更新された対応状態 |
| 人が確認する箇所 | 回答の根拠、更新対象、外部への送信前 |
| うまくいったと判断する条件 | 代表的な質問に根拠付きで答えられ、根拠がない場合はその旨を示す |

## 3. 中心となる処理を選ぶ

### 依頼に応じて対応を変えたいなら、Agentを中心にする

利用者とやり取りしながら情報を整理する、質問に答える、文章の下書きを作るなど、依頼ごとに進め方が変わる業務で検討します。

例：商談メモから次の対応案を考える、資料について追加質問する。

必要な資料やツールを設定し、代表的な依頼で試します。Agentを作るだけで、社内の全データや外部サービスを利用できるようになるわけではありません。

### 順序や分岐を定めたいなら、Workflowを中心にする

入力の取得、分類、条件に応じた処理、データ登録など、処理の流れを明示したい業務で検討します。

例：問い合わせ内容を分類し、分類に応じて必要な項目を抽出して記録する。

WorkflowはAgentを並べるだけの機能ではありません。必要な部分にAIモデルやAgentを組み込めます。**処理の順序を定めることと、AIの出力が毎回同じになることは別です。**

定期実行やイベント起点の起動が必要な場合も、まず入力から出力までの処理を確認し、その後に起動方法を選びます。起動方法の比較は[自動実行方式を選ぶ](choose-execution-method.md)で扱います。

### 共通の進め方を繰り返し使いたいなら、Skillを加える

Agentへの依頼で、同じ手順や確認項目、出力の作法を繰り返し使う場合に検討します。

例：報告書に含める項目や、調査時の確認順序をまとめる。

最初はAgentの指示で試し、再利用する範囲が見えてからSkillに整理する方法もあります。Skillは、Workflowの処理定義や外部サービスの認証設定の代わりではありません。

## 4. 必要な情報の扱い方を選ぶ

| 情報をどう扱いたいか | 検討する構成 | 選ぶときの注意 |
|---|---|---|
| 多くの資料から、質問に関係する説明を探したい | Agent＋Dataset | 資料の取り込みと参照設定が必要。検索結果だけで全文の網羅性は保証しない |
| 案件・タスクなどを項目ごとに登録・更新したい | Object＋必要な操作手段 | 項目、データの型、閲覧・更新範囲を決める |
| 添付資料や生成物をファイルとして保管したい | Storage＋必要な読み書き処理 | 保存だけでは検索・分析の処理は設定されない |
| 特定の文書を最初から最後まで確認・比較したい | ファイルを直接読み取る処理を検討 | 対応形式、読み取り範囲、容量などを確認。長文は章・ページ単位で処理し、未処理部分を管理する |
| 既存の外部サービスを参照・更新したい | 対応するツール・接続、または開発者による連携設計 | 対応操作、認証、実行主体、提供条件を確認する |

**資料の一部を探す業務と、資料を漏れなく確認する業務を区別してください。**

例えば、規程について質問に答える用途ではDatasetを検討できます。一方、契約書の全条項を比較する用途では、検索された箇所だけで済ませず、対象文書全体を処理できたか確認する設計が必要です。ファイルを直接渡す方法でも、全文が確実に読み取られたと決めつけないようにします。

また、既存の顧客管理システムなどに情報がある場合、同じ情報をすべてObjectへ複製することが最善とは限りません。どちらを正本にするか、更新をどのように反映するかを先に決めます。

## 5. 利用者向けの画面が必要かを決める

### チャットや既存の実行画面で足りる場合

質問や依頼を入力して結果を受け取るだけなら、まず既存の操作画面で試します。最初から専用のPageを作る必要はありません。

### 入力フォームや一覧が必要な場合

入力項目をそろえたい、複数のデータを一覧で見たい、決まった操作をボタンから実行したい場合は、Pageを検討します。

Pageには表示や操作の仕組みを作り、必要なデータや処理につなぎます。画面を用意するだけで、データ保存やAI処理まで自動的に完成するわけではありません。独自の画面や連携には、Web開発の知識が必要になる場合があります。

## 6. 業務別に、最初の構成を絞る

以下は設計の例です。設定済みで提供されるAppや、すべての環境で利用できる組み合わせを示すものではありません。

| 目的 | 最初に試す構成 | 必要になったら追加するもの | 最初の確認ポイント |
|---|---|---|---|
| 製品マニュアルを使い、回答の下書きを作る | Agent＋Dataset | Skill、問い合わせ記録用のObject | 根拠のある回答と、資料に答えがない質問への対応 |
| 問い合わせの分類・記録を定型化する | Workflow＋Object | 担当者が確認するPage | 分類結果、登録項目、失敗時に記録がどうなるか |
| チームのタスクを登録・更新する | Object＋利用可能なデータ操作画面 | Page、状況を整理するAgent | 項目と権限、必要な人が状態を更新できるか |
| レポートを同じ作法で繰り返し作る | Agent＋必要な元データ | Skill、定型部分のWorkflow、成果物用Storage | 必要な項目がそろい、数値と参照元を確認できるか |

迷った場合は、機能数の多さではなく、**代表的な1件を入力して、必要な結果まで確認できる構成か**を基準にします。

## 7. 構成が決まってから、作り方を選ぶ

「何を組み合わせるか」と「どう作成・操作するか」は別の判断です。

- **Web UI・AIによる構築支援**：画面で設定を確認したり、要件を伝えて構成を作ったりする方法を検討します。
- **SDK・CLI・API**：コードからの操作や連携が必要な場合に、開発者と対応範囲を確認します。

同じ機能でも、作成・編集・実行・参照のすべてを同じ方法で行えるとは限りません。SDKの実行場所やバージョン、認証方法、サーバー側の対応によっても範囲が異なります。APIを呼べることだけを根拠に、任意の外部本番システムとの連携がサポートされるとは判断しないでください。

具体的な選択は[Web UI・AI支援・SDK・CLI・APIを選ぶ](../development/choose-dev-path.md)で扱います。

## 作成を始める前のチェック

- [ ] 目的を「誰が・何を使って・何を得るか」で説明できる
- [ ] 既存のAppやProjectで対応できないか確認した
- [ ] 中心となる処理と、必要な情報の保存先・参照先を決めた
- [ ] 資料検索で足りるか、全文の確認が必要かを区別した
- [ ] 利用者、アクセス権、外部サービスの認証が必要な箇所を整理した
- [ ] データ更新・削除・外部送信の前に、人が確認する箇所を決めた
- [ ] テスト用の入力と、結果を確認する方法を用意した

目的に関係しない機能は、後から追加できます。まず必要な処理とデータで動作を確かめ、運用上の課題が見えてから画面や自動実行を加えていきます。
